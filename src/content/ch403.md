# 第三章 关键字与内存布局：编译器到底把东西放哪了

> 上一章的 `volatile` 只是提了一句"必须加"。这一章把它彻底讲清楚，顺便回答几个每次都会卡住新手的问题：为什么全局数组不能初始化太大？为什么 `sizeof` 比我算的多 4 个字节？为什么同一个结构体换一下成员顺序就变小了？

## 3.1 一份固件的五块地盘

编译出来的 `.bin` 烧进 Flash，运行时展开成五块区域。理解这张图，后面所有问题都能自己推出来：

```
        SRAM 0x2000_5000  ┌──────────────┐
                          │    Stack ↓   │  局部变量、返回地址，向下生长
                          │              │
                          │    Heap  ↑   │  malloc 分配，向上生长
          0x2000_0C00    ├──────────────┤
                          │    .bss      │  未初始化的全局/静态变量，启动时整段清零
          0x2000_0400    ├──────────────┤
                          │    .data     │  有初值的全局/静态变量，启动时从 Flash 拷来
          0x2000_0000    └──────────────┘

        FLASH 0x0800_2000 ┌──────────────┐
                          │    .text     │  机器码 + const 数据 + 字符串
        0x0800_0000       └──────────────┘
```

等价的一段 C 代码和它的归属：

```c
const uint8_t font[128] = {...};   /* .text  —— 待在 Flash，不占 RAM */
uint32_t g_tick = 0;               /* .bss   —— 零初始化，Flash 里不占空间 */
uint32_t g_state = 1;              /* .data  —— 初值存 Flash，运行时拷到 RAM */
void foo(void) { uint8_t b[16]; }  /* b 在 Stack */
void bar(void) { static uint8_t s[16]; }  /* s 在 .bss */
```


五个段各自的行为：

| 段 | 内容 | 存放位置 | 初始化方式 |
|---|---|---|---|
| `.text` | 机器码、`const` 数据、字符串字面量 | Flash | 烧录时写入 |
| `.data` | 有初值的全局/静态变量 | Flash（初值）→ RAM（运行） | 启动代码从 Flash 拷贝到 RAM |
| `.bss` | 无初值或初值为 0 的全局/静态变量 | RAM | 启动代码整段清零 |
| `Heap` | `malloc` 分配 | RAM | 运行时 |
| `Stack` | 局部变量、函数调用帧 | RAM | 运行时，向下生长 |

这张图解释了三件常被误解的事：

**为什么 `const` 数组越大越省 RAM？** 因为它待在 Flash 里，不占 RAM。在 F103 这种 20KB RAM 的芯片上，把字库、字模、字符串表全加上 `const`，能省下几 KB。

**为什么全局数组不能"随意初始化"？** 有初值的全局变量要在 `.data` 占一份 RAM，初值还要在 Flash 里存一份。而全零初始化的放 `.bss`，Flash 里一个字节都不占——所以 `uint8_t buf[1024] = {0};` 比 `= {1};` 省 1KB Flash。

**局部数组为什么危险？** 它在栈上。F103 的启动文件默认给 `Stack_Size` 只有 `0x400`（1KB）。一个 `uint8_t buf[2048]` 的局部数组就直接爆栈，表现为进函数就 HardFault——而且崩溃位置和原因看起来毫无关系，极难定位。

```c
/* startup_stm32f103xb.s 里改栈大小 */
Stack_Size      EQU     0x00000400    ; 默认 1KB，用了 RTOS 或深度递归要调大
```

**实用技巧**：编译后生成的 `.map` 文件里能查到每个段的确切占用，以及"哪个函数最占 Flash"。RAM 紧张时先看 `.bss` 里谁最大，往往能揪出一个没必要的全局缓冲。

## 3.2 static 的三种含义

同一个关键字，在三个位置是三种不同的意思。这是 C 语言里唯一这样的关键字：

```c
/* 含义一：函数内的静态局部变量 —— 生命周期变成整个程序，但作用域不变 */
void counter(void)
{
    static uint32_t n = 0;   /* 只初始化一次，存在 .data 而不是栈上 */
    n++;                      /* 每次调用都累加，函数返回后值保留 */
}

/* 含义二：文件级静态变量 —— 链接期不可见，其他 .c 文件引用不到 */
static uint32_t s_tick;      /* 名字不会进全局符号表，不会和其他文件冲突 */

/* 含义三：静态函数 —— 只在本文件内可见 */
static void helper(void) { }
```

在嵌入式里，**含义二和含义三是模块化设计的基础**。一个 `.c` 文件里所有不需要对外暴露的变量和函数，都应该加 `static`。好处有两个：

1. **不会撞名**。两个模块各自有一个 `static uint8_t inited`，编译链接完全不冲突；如果都不加 `static`，链接器会报"符号重复定义"
2. **编译器能更好地优化**。知道了"这个函数只在本文件用"，编译器敢做内联、敢删掉没调用的

一条工程纪律：**头文件里不要出现变量定义，只能有 `extern` 声明。** 在 `.h` 里写 `uint32_t g_tick;` 会被每个包含它的 `.c` 各定义一次，链接时报重复符号。

```c
/* 正确：module.h 里只声明 */
extern uint32_t g_tick;

/* 定义放在 module.c 里，只此一份 */
uint32_t g_tick = 0;
```

## 3.3 const 的四种组合

`const` 的第一个作用是让编译器帮你挡住误写，第二个作用是**把数据放到 Flash**（对 RAM 紧张的芯片是真实的收益）。

指针的 `const` 位置不同，含义完全不同。读法是**从右往左读**：

| 写法 | 从右往左读 | 谁能改 |
|---|---|---|
| `const char *p` | p 是指向 const char 的指针 | 内容不能改，指针能改 |
| `char * const p` | p 是 const 指针，指向 char | 指针不能改，内容能改 |
| `const char * const p` | p 是 const 指针，指向 const char | 都不能改 |
| `char const *p` | 同第一种（`const` 和 `char` 顺序无关） | 内容不能改 |

`const char *p` 是最常见的形态，表示"我不改你的字符串"。函数参数里凡是只读的指针都该加 `const`——这不仅是礼貌，它能让编译器发现你真改了。

一个容易踩的细节：**`const` 修饰的是"通过这个指针访问时只读"，不是"这块内存物理只读"。** 所以你仍然可以绕过去：

```c
const uint32_t table[4] = {1, 2, 3, 4};
uint32_t *p = (uint32_t *)table;   /* 强制去 const */
*p = 99;                            /* 编译通过，运行时可能写 Flash → HardFault */
```

在 MCU 上写 Flash 需要专门的解锁与擦除流程，直接写通常触发总线错误。这就是"const 变量放 Flash"的另一面：**去了 const 再写它，等于往只读存储器写，必然崩。**

## 3.4 volatile 的准确语义

`volatile` 是嵌入式里被误用最多的关键字。它只保证三件事：

1. **每次访问都真的去内存读写**，不使用寄存器里缓存的旧值
2. **不会删除"看起来没用"的访问**，比如连续两次读同一个地址，两次都会保留
3. **不会跨越 `volatile` 访问重排**（配合编译器的顺序保证）

它**不保证**的是：原子性、线程安全、内存屏障语义（那是 `atomic` 和 barrier 的事）。

### 典型错误

```c
/* 错误：flag 没加 volatile */
uint8_t flag = 0;

void EXTI0_IRQHandler(void) { flag = 1; }

int main(void)
{
    while (!flag) { }    /* -O2 下编译成 while(1) 空循环，永远出不来 */
}
```

编译器分析 `main`：`flag` 在这段循环里没有任何写入，于是把读操作提到循环外，只读一次。加上 `-O0` 能"正常"运行，一开优化就卡死——这是最经典的一类玄学 bug。

```c
/* 正确 */
volatile uint8_t flag = 0;
```

### 什么时候必须加 volatile

| 场景 | 原因 |
|---|---|
| 中断与主循环共享的变量 | 编译器看不到中断会改它 |
| 映射外设寄存器的成员 | 硬件会改，比如 `IDR`、`SR` |
| DMA 目标缓冲区 | DMA 控制器直接写内存，编译器不知道 |
| 忙等延时循环的计数器 | 否则可能被整体优化掉 |

```c
/* 这种延时循环，计数器不加 volatile 会被优化成空操作 */
void delay_loop(uint32_t n)
{
    volatile uint32_t i = n;
    while (i--) { }
}
```

### 什么时候不用加

- 只在单个函数内使用的局部变量
- 用 `__disable_irq()` 关中断保护好的临界区里的变量（关中断本身就阻止了并发访问）
- 用原子操作/互斥量保护的共享数据（保护机制已经带了屏障）

**`volatile` 加多了不是"更安全"，而是降低了优化效果。** 它会让每次访问都变成真实的内存读写，编译器没法把循环里的多次访问合并。乱加一气的代码能跑但会慢，而且掩盖了真正的并发问题。

## 3.5 结构体对齐：为什么 sizeof 比你算的大

规则只有一条：**每个成员的起始偏移，必须是它自身对齐数的整数倍**，不够就补填充字节。设前一个成员结束于 $\text{offset}_{i-1} + \text{size}_{i-1}$，则第 $i$ 个成员的偏移为：

$$
\text{offset}_i = \left\lceil \frac{\text{offset}_{i-1} + \text{size}_{i-1}}{\text{align}_i} \right\rceil \times \text{align}_i
$$

结构体总大小再取一次整：必须是**最大成员对齐数**的整数倍，因为只有这样，结构体数组里每个元素的成员才都能保持对齐。

```c
struct A {
    uint8_t  a;    /* 偏移 0 */
                   /* 偏移 1~3 填充（为了 b 的 4 字节对齐） */
    uint32_t b;    /* 偏移 4 */
    uint8_t  c;    /* 偏移 8 */
                   /* 偏移 9~11 填充（结构体总大小要按最大对齐数取整） */
};                 /* sizeof = 12 */

struct B {
    uint32_t b;    /* 偏移 0 */
    uint8_t  a;    /* 偏移 4 */
    uint8_t  c;    /* 偏移 5 */
                   /* 偏移 6~7 填充 */
};                 /* sizeof = 8 */
```

同样的数据，成员顺序不同，大小差 4 字节。规则是两条：

1. 每个成员的偏移必须是**自身大小的整数倍**（`uint32_t` 要 4 字节对齐）
2. 结构体总大小必须是**最大成员对齐数的整数倍**（否则数组里第二个元素会错位）

在 RAM 只有几 KB 的芯片上，这个规则值得利用：**把大成员放前面，把小的挤在后面**。一个有 10 个成员的配置结构体，排好序能省 20~30 字节；如果这个结构体要开 100 个实例，就是 2~3KB。

### packed 的代价

```c
/* 强制取消填充，按字节紧排（sizeof 变成 5） */
struct __attribute__((packed)) Frame {
    uint8_t  head;
    uint32_t id;
};
```

`packed` 常用于解析通信协议帧——协议里字段是紧排的，如果结构体有填充就对不上。但代价很实在：

- **访问变慢**。非对齐的 `uint32_t` 访问在 Cortex-M0 上直接 HardFault；在 M3/M4 上硬件能处理，但要拆成两次访问，慢一倍以上
- **不能取成员地址传给别的函数**。取到的地址本身非对齐，别人按对齐假设访问会崩

所以推荐的折中做法是：**协议解析不用结构体直接映射，而是手动按字节组装**。

```c
/* 稳妥写法：按字节解析，无对齐问题，字节序明确 */
uint32_t parse_u32_le(const uint8_t *p)
{
    return (uint32_t)p[0] | ((uint32_t)p[1] << 8) |
           ((uint32_t)p[2] << 16) | ((uint32_t)p[3] << 24);
}
```

## 3.6 字节序：跨设备通信的第一道坑

Cortex-M 是小端（低字节放低地址）。`uint32_t x = 0x12345678` 在内存里是：

```
地址:  0x00  0x01  0x02  0x03
内容:  0x78  0x56  0x34  0x12
```

这意味着**用 `memcpy` 或指针强转把结构体直接发到串口，对方收到的字节顺序取决于双方 CPU**。两个小端设备之间没事，一旦对面是大端（部分 DSP、某些工业协议）就全错位。

工业协议（Modbus、CANopen）都是**明确规定了字节序**的，必须手动组帧，不能偷懒发结构体：

```c
/* Modbus 用大端（网络字节序） */
buf[0] = (val >> 8) & 0xFF;
buf[1] =  val       & 0xFF;
```

另一个坑是**联合体（union）看字节**的写法：

```c
union { uint32_t u; uint8_t b[4]; } v;
v.u = 0x12345678;
/* v.b[0] == 0x78（小端），大端机器上是 0x12 */
```

这种代码能跑，但**换平台就变**。除了刻意做字节序探测，不建议这么写。

## 3.7 栈：最容易被忽视的资源

默认栈只有 1KB。以下行为会快速吃掉它：

| 行为 | 栈消耗 |
|---|---|
| 局部 `uint8_t buf[256]` | 256 B |
| 局部 `float mat[3][3]` | 36 B |
| 递归 10 层，每层 100 B 局部变量 | 1 KB（直接爆） |
| `printf("%f", x)` | 浮点格式化内部可能用几百字节 |

三条实用规则：

1. **大缓冲区一律 `static` 或全局**，不要放栈上。加了 `static` 就进 `.bss`，不占栈
2. **不要在中断里用大局部变量**。中断用的是当前任务的栈，栈本来就在用，中断再压一层容易爆
3. **不要在主循环里 `printf` 浮点**。`%f` 会拉进几百字节的格式化代码和栈空间，Flash 和 RAM 双重开销

爆栈的表现是 HardFault，但**崩溃位置往往在别处**（栈溢出踩坏了某个不相关的变量或返回地址）。查这类问题最有效的手段是"填充法"：启动时把栈区填成 `0xCDCDCDCD`，跑一段时间后看最深被写到哪，就知道实际用了多少。

## 3.8 这一章要带走的东西

1. 五段：`.text` Flash 常驻、`.data` 有初值全局、`.bss` 零初始化、heap、stack
2. `const` 数据放 Flash，字模字库加 `const` 能真实省下 RAM
3. 局部大数组是爆栈主因，1KB 默认栈很容易踩穿
4. `static` 三种含义：静态局部、文件级私有变量、私有函数。后两种是模块化的基础
5. 头文件只放 `extern` 声明，定义放 `.c`，否则链接重复定义
6. `const` 在指针的位置决定"谁能改"，从右往左读
7. `volatile` 保证每次都真读内存、不删访问、不跨它重排；它**不保证**原子性
8. 共享于中断和主循环的变量必须 `volatile`，但不要滥用
9. 结构体有填充，大小成员顺序会影响 `sizeof`；`packed` 有对齐代价，协议解析建议手动按字节组装
10. Cortex-M 是小端，跨设备通信必须明确字节序

下一章把这些串起来：当 `volatile` 加上中断、DMA、多任务，光"每次都真读"已经不够了——你需要考虑**原子性**和**执行顺序**。
