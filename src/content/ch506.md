## 6.1 FreeRTOS 的五种内存管理方案

FreeRTOS 把「堆管理」做成了可替换的插件，文件名为 `heap_1.c` ~ `heap_5.c`，编译时选一个链接进去。`xTaskCreate`、`xQueueCreate` 等动态创建 API 的内存都从这里拿。

| 方案 | 特点 | 适用 |
| --- | --- | --- |
| heap_1 | 只分配、不释放，启动即定型 | 永不删除任务的极简系统 |
| heap_2 | 分配+释放，但不合并碎片 | 已淘汰，基本不用 |
| heap_3 | 简单包了一层标准 `malloc/free` | 想直接用 libc 堆时 |
| **heap_4** | 分配+释放+**合并相邻空闲块**，最常用 | 绝大多数项目首选 |
| heap_5 | 在 heap_4 基础上支持**不连续的多块内存区** | 有片外 SRAM 等分散内存 |

本平台示例与绝大多数产品都选 **heap_4**：它能把释放出来的相邻块合并，显著降低长期运行的碎片。但要注意，heap_4 仍然**不是通用内存分配器**——它没有防护、没有线程无关的复杂策略，频繁地创建/删除大量小对象依然会碎。

## 6.2 总堆大小与任务栈的来源

`configTOTAL_HEAP_SIZE` 决定了 FreeRTOS 这一整块堆有多大（比如 10KB）。任务栈、TCB、队列、信号量全从这 10KB 里扣。所以：

```c
#define configTOTAL_HEAP_SIZE    ((size_t)(10 * 1024))   // 10KB 给 RTOS 用
```

栈的大小在 `xTaskCreate` 的第三个参数指定（单位是**字**，4 字节），它**从 RTOS 堆里分配**。如果总堆不够，创建任务会返回 `NULL` 或 `errCOULD_NOT_ALLOCATE_REQUIRED_MEMORY`——新手常忽略这个返回值，拿到失败的任务句柄就去用，随即崩溃。

## 6.3 五大经典坑

**坑一：栈溢出。** 函数嵌套深、局部数组大（比如 `uint8_t buf[512]`）、用了浮点，都会吃栈。`uxTaskGetStackHighWaterMark()` 返回「历史最低剩余栈」，数值小说明快溢出了。正确做法：先开大（如 1KB），跑起来用水位线反推真实需求，再收紧。**宁可在栈上浪费几百字节 RAM，也不要溢出。**

**坑二：堆碎片。** 一个任务每秒创建又删除一个队列、一个对象，跑几天后 `xQueueCreate` 开始失败，就是碎片作祟。对策：① 用 heap_4 而非 heap_2；② **静态创建**（给一块固定数组，不进堆）；③ 高频对象在初始化时一次建好，运行中复用，绝不反复 new/delete。

**坑三：优先级反转。** 见第四章——共享资源用**互斥量**而非信号量来保护，互斥量的优先级继承能拉平反转。

**坑四：死锁（Deadlock）。** 任务 A 拿了锁 1 去等锁 2，任务 B 拿了锁 2 去等锁 1，两边互相等，系统假死。对策：**所有任务按固定顺序加锁**（永远先锁 1 再锁 2），或给 `Take` 设超时 `xSemaphoreTake(m, pdMS_TO_TICKS(100))` 而不是无限等，超时即告警而非干等。

**坑五：在 ISR 调错 API。** 见第五章——中断里只用 `...FromISR()` 版本，且只有优先级 ≥ `configMAX_SYSCALL_INTERRUPT_PRIORITY` 的中断才能调。

## 6.4 静态 vs 动态创建

除了动态 `xTaskCreate`，FreeRTOS 还提供静态版本：

```c
StaticTask_t tcb;                  // 你自己定义的 TCB 内存
StackType_t  stack[256];          // 你自己定义的栈内存
TaskHandle_t h = xTaskCreateStatic(task, "t", 256, NULL, 2, stack, &tcb);
```

静态创建**不碰 RTOS 堆**，没有分配失败、没有碎片，行为完全确定，适合对可靠性要求极高的安全关键系统（如医疗设备、车规）。代价是 RAM 布局要你手动规划。动态创建胜在灵活、代码少。两者可混用。

## 6.5 三个必会的水位/状态诊断 API

调试 RTOS 内存与调度问题，这三个是利器：

- `uxTaskGetStackHighWaterMark(handle)`：任务历史最低栈余量，决定栈该开多大；
- `xPortGetFreeHeapSize()`：RTOS 堆还剩多少字节；
- `uxTaskGetSystemState(...)`：一次性导出所有任务的状态、栈底、运行时间，配合上位机看板做系统体检。

建议在开发期把 `configCHECK_FOR_STACK_OVERFLOW` 和 `configUSE_MALLOC_FAILED_HOOK` 都打开，栈溢出和分配失败会直接进 Hook，第一时间暴露问题，而不是等它演变成诡异的 HardFault。

## 6.6 一句话收尾

RTOS 把「多任务」这件难事接了过去，但**内存还是你自己的责任**：栈给够、堆留余量、别在运行期疯狂分配释放、用对同步原语。把这套纪律养成习惯，STM32 上的多任务系统就能稳稳跑上电、跑过温循、跑过长期老化。

不过在这一章收尾之前，还有一件天天要用、却总被跳过的小事：**周期动作**。灯要闪、屏要刷、超时要检测、数据要定时上报——为每件事开一个任务太浪费栈，用硬件定时器又根本不够用（F103C8T6 上能用的通用定时器只有三个，还得留给 PWM）。

下一章讲软件定时器：它凭什么能用一个任务管住几十个定时器，为什么它的回调绝对不能阻塞，以及它和硬件定时器的精度差在哪里。
