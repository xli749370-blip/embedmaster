## 5.1 临界区：一段不能被打断的操作

所谓**临界区（Critical Section）**，就是「这一段代码在执行期间，不能被别的任务或中断插进来」的保护区。典型需要保护的场景：改一个被多任务共享的全局计数器、操作一个非原子硬件寄存器、往一个共享链表里插入节点。

如果临界区被中途打断，就会出现上一章说的竞态。所以进入临界区要「挡住打扰」，出去再「放开」。FreeRTOS 提供两层挡法：

- **调度锁** `vTaskSuspendAll()` / `xTaskResumeAll()`：只阻止**任务切换**，中断照样能进。适合「我要快速改一下共享结构，但不想被切到别的任务」的场景。
- **临界区** `taskENTER_CRITICAL()` / `taskEXIT_CRITICAL()`：直接**关中断**（仅关到 `configMAX_SYSCALL_INTERRUPT_PRIORITY` 以下的可管理中断），任务切换和大多数中断都被挡住。保护最彻底，但代价也最大。

## 5.2 关中断的代价：时间就是实时性

关中断期间，任何中断都进不来。这意味着：

- 如果此刻串口正在收数据，数据可能因为 RDR 没及时读走而溢出（ORE）；
- 如果系统节拍被挡在外面，延时、超时都会失真；
- 最坏情况是**高优先级紧急中断被憋住**，破坏系统的实时性保证。

所以临界区铁律：**能短则短，里面只做「读-改-写」三两行，绝不放任何阻塞调用、绝不调 `vTaskDelay`、绝不调可能阻塞的 API。** 临界区里调 `xQueueReceive(..., portMAX_DELAY)` 会直接死锁——因为关了中断，唤醒你的那个中断永远进不来。

## 5.3 中断优先级：和任务优先级不是一回事

这里要再次强调那个反直觉的点：**任务优先级（FreeRTOS，数字大=高）和中断优先级（Cortex NVIC，数字小=高）是两套独立体系。**

FreeRTOS 把中断优先级划成两半：

- **≥ `configMAX_SYSCALL_INTERRUPT_PRIORITY`**（数值较大、优先级较低）的中断：**可以**调用 `...FromISR()` 系列 API；
- **< `configMAX_SYSCALL_INTERRUPT_PRIORITY`**（数值较小、优先级较高）的中断：**绝对不能**调用任何 FreeRTOS API，连 FromISR 版都不行，否则会破坏内核临界区，导致随机崩溃或 HardFault。

为什么这么设计？因为内核的临界区是「关到某个优先级以下」实现的。如果一个优先级比它还高的中断去碰内核数据，内核的关中断保护就罩不住它了。所以**真正硬实时的高优先级中断（比如电机堵转保护），应当完全不依赖 RTOS，自己短平快处理完就走。**

## 5.4 中断与任务的边界：ISR 里只做三件事

一条被反复验证的工程纪律：**中断服务函数里只做「读数据、清标志、发信号」，重活留给任务。**

```c
void TIM2_IRQHandler(void) {
    TIM2->SR &= ~TIM_SR_UIF;                  // 1. 清标志（必须！否则反复进中断）
    BaseType_t woken = pdFALSE;
    xQueueSendFromISR(q, &sample, &woken);    // 2. 把数据丢给任务
    portYIELD_FROM_ISR(woken);                // 3. 必要时立即切换
}
```

这样做的好处：

- ISR 极短，关中断/高优先级占用时间最小，实时性最好；
- 复杂的计算、打印、协议解析都在任务上下文做，可以阻塞、可以用全套 API；
- 调试友好：ISR 出错概率大幅下降。

## 5.5 别在 ISR 里干这些事

以下操作在中断上下文里是**致命**的：

- 调 `printf` / `sprintf`：内部有锁、可能阻塞，还会拖长中断；
- 调 `malloc` / `free`：堆操作非原子，会破坏内核或其他任务的堆；
- 调非 FromISR 版的队列/信号量函数：`xQueueSend` 在 ISR 里调用是未定义行为；
- 调 `vTaskDelay` 或任何会阻塞的 API：中断里没有「任务」概念，阻塞等于系统卡死；
- 忘了清中断挂起标志：标志不清，退出 ISR 后立刻又被拉回来，表现为「程序卡在中断里」。

## 5.6 优先级天花板 vs 优先级继承

互斥量用「优先级继承」解决反转，但还有一种更激进的算法叫**优先级天花板（Priority Ceiling）**：一旦任务拿到某把锁，它的优先级立刻被抬到「所有可能竞争这把锁的任务里的最高优先级」。天花板协议能彻底杜绝死锁，但实现更复杂、灵活性低，FreeRTOS 的互斥量采用的是继承协议。

无论哪种，核心思想一致：**通过临时抬升持锁任务的优先级，缩短它被中间优先级任务插队的时间窗口。** 理解这一点，你就能看懂为什么「拿锁的瞬间系统行为会变」。

## 5.7 一个排查清单

当你的 RTOS 程序出现「偶发卡死、进 HardFault、数据错乱」时，按这个顺序查中断相关问题：

1. ISR 里有没有调用非 FromISR 的 API？（最常见）
2. ISR 有没有清中断标志？（忘了清 → 反复进）
3. 临界区里有没有调阻塞 API？（死锁）
4. 用 FreeRTOS API 的中断，优先级有没有 ≥ `configMAX_SYSCALL_INTERRUPT_PRIORITY`？
5. 临界区是不是太长，导致丢中断 / 实时性劣化？

把这几条刻进肌肉记忆，能省下无数个通宵的调试。
