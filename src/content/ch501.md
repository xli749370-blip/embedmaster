## 1.1 从「裸机前后台」说起

没有操作系统的单片机程序，绝大多数长这样：

```c
int main(void) {
    init_gpio();
    init_uart();
    while (1) {
        if (key_pressed())  handle_key();   // 前台：主循环轮询
        read_sensor();                       // 前台：采样
        send_uart();                         // 前台：上报
        HAL_Delay(10);                       // 前台：等一下
    }
}

void USART1_IRQHandler(void) {              // 后台：中断
    recv_byte = USART1->DR;
}
```

这种结构叫**前后台系统**：`while(1)` 是「前台」，负责所有顺序逻辑；中断是「后台」，负责异步事件。它简单、直观、资源占用极小，做一个按键控制 LED、读个温湿度上传，完全够用。

但业务一复杂，麻烦就来了。

## 1.2 三个躲不掉的痛点

**痛点一：时序互相打架。** 你想让 LED 每 500ms 闪一次，同时串口一旦收到命令要 10ms 内响应，同时 ADC 要按 1kHz 稳定采样。可主循环是「一条道走到黑」的——上一行 `HAL_Delay(10)` 就把 CPU 占住了，这 10ms 里按键、串口、采样全被卡住。所谓的「同时做几件事」，在裸机里只能靠把 `delay` 拆成状态机、把大循环拆成时间片，**代码会迅速变成一团谁也看不懂的状态位**。

**痛点二：空等浪费 CPU。** 任务 B 要等任务 A 算完才能继续。裸机里写不出「等 A 的时候我去干别的」，只能 `while(!flag);` 原地空转，或者 `HAL_Delay` 死等。CPU 要么空转、要么睡死，永远处在两个极端。

**痛点三：模块越缠越紧。** 所有逻辑挤在同一个大循环里，温控、通信、显示共享一堆全局变量。改一处，别处莫名其妙跟着错。这就是所谓的「意大利面代码」，维护成本随代码量呈平方上升。

## 1.3 RTOS 给出的答案

实时操作系统（RTOS）不帮你算 PID、不帮你画 PCB，它只解决一件事：**让多个任务看起来像同时运行，且各自干净独立。**

它的三件核心武器：

- **任务（Task）**：每个任务是一段独立的死循环函数，拥有**自己的栈和优先级**。任务 A 卡住了，不影响任务 B 运行。
- **抢占式调度**：调度器永远让「优先级最高且就绪」的任务占用 CPU。高优先级任务一就绪，立刻把低优先级任务挤下去（抢占）。
- **阻塞式等待**：任务想等数据时，调用 `vTaskDelay()` 或 `xQueueReceive()` 进入「阻塞」状态，把 CPU 让出来给别人。它**不空等**——这是和裸机最本质的区别。

用 RTOS 重写上面的例子，会变成三个任务：

```c
void task_led(void *p)   { for (;;) { toggle_led(); vTaskDelay(pdMS_TO_TICKS(500)); } }
void task_uart(void *p)  { for (;;) { if (uart_recv(&c)) handle(c); } }
void task_sensor(void *p){ for (;;) { adc_sample(); vTaskDelay(pdMS_TO_TICKS(1)); } }
```

三个任务各写各的，互不关心对方，调度器负责在它们之间切来切去。LED 任务在 `vTaskDelay` 期间并不占 CPU，那 500ms 里 CPU 去跑了采样和串口。

## 1.4 一个反直觉的事实

> **RTOS 不是让程序跑得更快，而是让程序「更确定、更好组织」。**

单看一段代码的执行速度，裸机直跑永远比 RTOS 快——因为 RTOS 每次切换要保存/恢复几十个寄存器（上下文切换开销，典型几微秒）。RTOS 的价值在**系统层面**：

- 高优先级事件（比如急停按钮）能在微秒级被响应，不被低优先级的慢任务拖累；
- 每个模块边界清晰，加功能只是加一个任务，不碰别人的代码；
- 复杂的时序靠调度器保证，你不用手写状态机去抠每一个微秒。

## 1.5 RTOS 也有代价，别盲目上

| 维度 | 裸机前后台 | RTOS |
| --- | --- | --- |
| RAM 占用 | 几乎只有关心全局变量 | 每个任务一个栈（常 512B~2KB），还有内核堆 |
| 实时性上限 | 取决于你状态机写多好 | 由调度器与中断延迟决定，更稳定 |
| 代码复杂度 | 简单项目低，复杂项目爆炸 | 起步有学习成本，复杂项目反而省心 |
| 适用 | 单功能、小 RAM（如 8 位 MCU） | 多外设、多时序、需要长期维护的项目 |

经验法则：**资源极度紧张（RAM < 2KB）、功能单一、写一次不再改**的项目，裸机更合适；**功能多、要长期迭代、团队开发**，上 RTOS。STM32F103（20KB RAM）跑 FreeRTOS 绰绰有余，这正是本平台的主战场。

## 1.6 本课程的基准与路线

本课程以 **FreeRTOS**（最流行的开源 RTOS，已被 AWS 收购并长期维护）为讲解基准，但讲清楚的概念对 RT-Thread、Zephyr 同样适用。后面五章依次讲：

1. 任务与调度（优先级、时间片、就绪表）；
2. 上下文切换与任务栈（配合一页交互动画）；
3. 同步与通信（信号量、互斥量、消息队列）；
4. 临界区与中断管理；
5. 内存管理与五大经典坑。

读完你应该能回答：什么时候该用队列、什么时候用互斥量、为什么中断里调用 API 会崩、栈开多大才安全。
