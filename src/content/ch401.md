# 第一章 指针与地址：变量到底住在哪

> 学 C 语言的人分两类：一类觉得指针很难，一类知道指针只是"存地址的变量"。这两类人的区别不在于智商，而在于有没有真正看过内存。这一章我们就把内存摊开来看。

## 1.1 变量住在哪

在 STM32 上写 `uint32_t cnt = 100;`，编译器做了三件事：

1. 在 RAM 里挑一个地址，比如 `0x20000004`
2. 把 100 按小端序写成 4 个字节：`64 00 00 00`
3. 之后代码里所有 `cnt` 都翻译成"从 `0x20000004` 开始的 4 个字节"

**变量名是给人看的，机器只认地址。** 这句话是理解指针的全部前提。变量名在编译后根本不存在——它只是编译器帮你记住"100 存在哪"的便签。

所以在嵌入式里，我们随时可以绕过编译器自己算地址：

```c
/* 直接读写 0x20000004 这 4 个字节，不声明任何变量 */
*(volatile uint32_t *)0x20000004 = 200;
```

这行代码合法、常用，而且正是 HAL 库操作寄存器的本质。它说明：**地址是比变量更底层的东西。**

## 1.2 指针到底是什么

指针就是一个**存地址的变量**。它自己也有地址，也在 RAM 里占地方——这点很多人绕不过来。

```c
uint32_t cnt = 100;      /* 变量：地址 0x20000004，值 100 */
uint32_t *p = &cnt;      /* 指针：地址 0x2000000C，值 0x20000004 */
```

拆开看三个符号：

| 写法 | 读法 | 得到什么 |
|---|---|---|
| `cnt` | cnt 的值 | `100` |
| `&cnt` | cnt 的地址 | `0x20000004` |
| `p` | p 的值 | `0x20000004` |
| `*p` | p 指向的那个东西的值 | `100` |
| `&p` | p 自己的地址 | `0x2000000C` |

`*` 在**声明**时表示"这是个指针"，在**表达式**里表示"顺着地址去取值"。同一个符号两种含义，这是 C 语言最坑的设计之一。看到 `uint32_t *p;` 时，把它读成"`*p` 是 `uint32_t`"，指针类型就永远不会看错。

### 类型决定了什么

指针的类型不决定它占多大空间（在 32 位 STM32 上所有指针都是 4 字节），只决定两件事：

1. **解引用时读几个字节**：`uint8_t *` 读 1 个，`uint32_t *` 读 4 个
2. **指针算术时走多远**：`p + 1` 到底加 1 还是加 4

第 2 点是最容易出错的地方，下一节单独讲。

## 1.3 指针算术：+1 到底加多少

这是指针区别于"整数地址"的核心。`p + 1` **不是**地址加 1，而是加 `sizeof(*p)`。

```c
uint8_t  *p8  = (uint8_t *)0x20000000;
uint16_t *p16 = (uint16_t *)0x20000000;
uint32_t *p32 = (uint32_t *)0x20000000;

p8  + 1;   /* 0x20000001，走了 1 字节 */
p16 + 1;   /* 0x20000002，走了 2 字节 */
p32 + 1;   /* 0x20000004，走了 4 字节 */
```

写成公式就是：

$$
\text{addr}(p + n) = \text{addr}(p) + n \times \text{sizeof}(*p)
$$

编译器需要知道 `*p` 的类型才能算出这个乘法，这就是为什么 C 里**不能对 `void *` 做算术**——`sizeof(void)` 无意义。同理，把 `p16` 强转成 `p8` 再 `+1`，走的距离会从 2 字节变成 1 字节，指针类型和"指向什么"必须始终一致。

编译器在背后偷偷做了一次乘法：`地址 + n * sizeof(*p)`。这个设计让数组访问成为可能——`buf[i]` 编译后就是 `*(buf + i)`，不用手动乘元素大小。

代价是：**类型搞错，地址就会错位。** 下面这个 bug 我见过太多次：

```c
uint16_t buf[100];
uint8_t *p = (uint8_t *)buf;

p[1] = 0xFF;        /* 改的是 buf[0] 的高字节，不是 buf[1]！ */
```

记住这个规律：**指针算术的单位是"元素"，不是"字节"。** 想按字节移动，就用 `uint8_t *` 或者 `char *`（这也是 `memcpy` 内部用 `char *` 的原因）。

## 1.4 数组名不是指针

初学者常听"数组名就是指针"，这句话是**错的**，至少有两个致命区别：

```c
uint8_t buf[10];

sizeof(buf);      /* 10 —— 整个数组的大小 */
sizeof(p);        /* 4  —— 指针本身的大小 */

buf = p;          /* 编译错误！数组名不是左值，不能被赋值 */
p = buf;          /* 合法：数组名退化为指向首元素的指针 */
```

准确的说法是：**数组名在大多数表达式里会"退化"成指向首元素的指针，但它本身是一个数组对象。**

退化规则只在三个例外下不生效：`sizeof(buf)`、`&buf`、以及用字符串字面量初始化字符数组时。

`&buf` 和 `buf` 的值相同，但类型不同——`&buf` 是 `uint8_t (*)[10]`，`&buf + 1` 会跳 10 个字节。这就是"类型决定步长"的又一次体现。

### 二维数组与指针数组

嵌入式里经常需要一张常量查找表，这时二维数组比指针数组更省空间：

```c
/* 指针数组：每行一个指针(4B) + 字符串本身，指针额外占 12 字节 */
const char *names[] = { "idle", "run", "fault" };

/* 二维数组：连续 12 字节，无额外开销，但每行等长 */
const char names2[3][6] = { "idle", "run", "fault" };
```

在只有 20KB RAM 的 F103 上，这种差别是要计较的。

## 1.5 函数参数：为什么必须传指针

C 语言**只有值传递**。函数拿到的永远是实参的副本，改副本不影响原件。

```c
void bad(uint32_t x)  { x = 100; }        /* 外面看不到变化 */
void good(uint32_t *x) { *x = 100; }      /* 通过地址改到了原件 */

uint32_t v = 0;
bad(v);      /* v 还是 0 */
good(&v);    /* v 变成 100 */
```

大结构体作为参数时，值传递还会复制整个结构体，既慢又费栈。标准做法是传 `const 指针`：

```c
/* 只读访问，加 const 让编译器帮你挡住误写，同时表明"我不改你的数据" */
void send_frame(const Frame *f);
```

这条 `const` 不是装饰。它会让"不小心在函数里改了入参"从运行时的疑难杂症变成编译期的报错。

## 1.6 二级指针什么时候真的需要

`uint8_t **pp` —— 指向指针的指针。初学者常被作业逼着学，觉得很抽象。其实它只解决一类问题：**函数需要修改"调用者的指针变量本身"**。

最典型的场景是让函数分配内存并返回：

```c
/* 错误写法：改的是局部副本 p，外面的指针没变 */
void alloc_bad(uint8_t *p) { p = malloc(100); }

/* 正确写法：把"指针变量的地址"传进去 */
uint8_t alloc_ok(uint8_t **pp, uint32_t len)
{
    *pp = malloc(len);
    return (*pp == NULL) ? 1 : 0;
}
```

另一个常见用法的场景是链表操作：删除头节点时必须改头指针，只能靠二级指针（或返回新头指针）。

**判断标准很简单**：函数要改的是"数据"还是"指针本身"？改数据传一级，改指针传二级。

## 1.7 五个必踩的坑

### 坑一：野指针

```c
uint32_t *p;      /* 没初始化，p 里是栈上的随机垃圾 */
*p = 1;           /* 往一个随机地址写 1 —— 可能直接 HardFault */
```

规则：**指针声明时就初始化为 `NULL`**。`NULL` 解引用至少是确定的崩溃，野指针的崩溃地址每次都不一样，根本没法查。

### 坑二：返回局部变量的地址

```c
uint32_t *bad(void)
{
    uint32_t local = 42;
    return &local;    /* local 在函数返回时已销毁，栈会被复用 */
}
```

编译器通常会给 warning，但不会报错。这种代码 90% 的时间"看起来正常"，然后在某个改动了调用顺序的版本里突然出错——最难查的一类 bug。

### 坑三：解引用前不判空

```c
if (p != NULL && *p > 0) { ... }   /* 短路求值保证安全 */
if (*p > 0 && p != NULL) { ... }   /* 顺序反了，p 为空时已经崩了 */
```

### 坑四：越界写

```c
uint8_t buf[8];
for (uint32_t i = 0; i <= 8; i++) buf[i] = 0;   /* i == 8 越界 */
```

在 PC 上可能只是悄悄改坏了相邻变量；在 MCU 上，越界可能踩到栈帧里的返回地址，直接跑飞去执行随机指令。`<=` 写成 `<` 这类错误，用 `for (i = 0; i < ARRAY_LEN(buf); i++)` 配合宏能挡掉一大半。

### 坑五：`malloc` 后不判空

```c
uint8_t *p = malloc(1024);
memset(p, 0, 1024);    /* 内存不足时 p 为 NULL，直接崩 */
```

嵌入式里堆空间通常只有几 KB，`malloc` 失败是常态而不是异常。

## 1.8 嵌入式特有的指针用法

### 访问固定地址

MCU 的外设寄存器地址是芯片手册写死的。HAL 库用结构体把它们组织起来，本质是"把一个地址强制转成结构体指针"：

```c
#define GPIOA_BASE  0x40010800UL

typedef struct {
    volatile uint32_t CRL;    /* 偏移 0x00 */
    volatile uint32_t CRH;    /* 偏移 0x04 */
    volatile uint32_t IDR;    /* 偏移 0x08 */
    volatile uint32_t ODR;    /* 偏移 0x0C */
} GPIO_TypeDef;

#define GPIOA  ((GPIO_TypeDef *)GPIOA_BASE)

GPIOA->ODR |= (1U << 5);      /* 点亮 PA5 上的 LED */
```

这里有两个关键点：

- `volatile` 告诉编译器"这个值随时可能被硬件改动，每次都老老实实去读，别优化到寄存器里"
- 结构体成员的偏移必须和手册一致，靠的是编译器按声明顺序连续排布——所以这个结构体里**不能有填充**（全是 4 字节成员自然对齐，不会有 padding）

### 用指针实现环形缓冲区

串口 DMA 收数据几乎都靠环形缓冲区，核心就是两个指针（或索引）在数组里绕圈：

```c
typedef struct {
    uint8_t buf[256];
    volatile uint16_t head;    /* 写入位置，只在 ISR 里前进 */
    volatile uint16_t tail;    /* 读取位置，只在主循环里前进 */
} RingBuf;

/* 剩多少字节可读：自动处理回绕 */
uint16_t ring_count(const RingBuf *r)
{
    return (uint16_t)((r->head - r->tail) & 0xFF);   /* 256 是 2 的幂，用位与代替取模 */
}
```

`head` 和 `tail` 都被 `volatile` 修饰，因为它们会被中断和主循环同时访问。这个 `volatile` 不是可选项——去掉它，编译器在 `-O2` 下会把 `head` 缓存进寄存器，主循环永远看不到新数据。

## 1.9 这一章要带走的东西

1. 变量名只是地址的别名，指针是存地址的变量，指针自己也有地址
2. `*` 在声明和表达式里含义不同：读成"`*p` 是 `uint32_t`"就不会看错
3. 指针算术的单位是元素不是字节，`p + 1` 加的是 `sizeof(*p)`
4. 数组名会退化成指针，但它不是指针，`sizeof` 和赋值行为完全不同
5. C 只有值传递，想改外部变量就传地址；不想改就加 `const`
6. 二级指针用于修改"指针本身"，不是用来炫技
7. 野指针、返回局部地址、不判空、越界、`malloc` 不判空——这五个坑占嵌入式 bug 的一大半

下一章我们进入位操作。指针解决的是"数据在哪"，位操作解决的是"这 32 位里每一位是什么意思"——后者才是写寄存器的主要工作。
