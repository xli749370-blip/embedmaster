# 第五章 串口与 printf 重定向：把芯片内部的情况看见

> 嵌入式调试有个残酷的现实：你没有显示器，没有断点日志，甚至可能连调试器都没接。串口是唯一一条几乎零成本、到处都能用的"输出通道"。会配串口不难，难的是配得稳——不丢数据、不阻塞、不因为一个字节出错就永久卡死。

## 5.1 一帧数据长什么样

UART 是异步通信，没有时钟线，靠双方约定好的波特率对齐。一帧数据的结构：

```
空闲(高)  起始位   D0  D1  D2  D3  D4  D5  D6  D7  校验位  停止位  空闲(高)
  ────┐    ┌──┐
      └────┘  └── ... 数据位 ... ──┘  └──┘  └────┘
```

| 部分 | 位数 | 说明 |
|---|---|---|
| 起始位 | 1 | 固定低电平，标志一帧开始 |
| 数据位 | 5–9 | 常用 8 位，**低位先发** |
| 校验位 | 0 或 1 | 奇/偶校验，只检错不纠错 |
| 停止位 | 0.5 / 1 / 1.5 / 2 | 常用 1 位，固定高电平 |

最常用的配置简写为 **8N1**：8 个数据位、无校验、1 个停止位。这是绝大多数模块（GPS、蓝牙、WiFi、传感器）的默认配置，也是新项目应该优先选的。

**为什么常用 8N1 而不是带校验？** 因为校验位只能发现单比特错误，而现代链路层协议（Modbus、自定义帧头帧尾 + CRC）在上层做得更可靠。加了校验位反而让每帧多占 1 位带宽，且和很多模块的固定配置不兼容。

**光看结构还不够，波形上每一位的位置和宽度才是关键。** 下面这个动画把一帧拆成 12 个位格，可以切换波特率与发送字节，观察"高位在左、线上低位先发"到底长什么样——这是串口调试时最容易被搞混的一点。

## 5.2 波特率：误差从哪来

波特率由外设时钟分频得到：

$$
\text{USARTDIV} = \frac{f_{PCLK}}{16 \times \text{BaudRate}}
$$

以 72MHz、115200bps 为例：

$$
\text{USARTDIV} = \frac{72000000}{16 \times 115200} = 39.0625
$$

小数部分 0.0625 恰好能被 4 位小数分频器精确表示（0.0625 = 1/16），所以**误差为 0**，这是 72MHz 时钟下 115200 特别稳的原因。

换成 9600bps：

$$
\text{USARTDIV} = \frac{72000000}{16 \times 9600} = 468.75
$$

0.75 同样能精确表示，误差为 0。

但如果是 250000bps：

$$
\text{USARTDIV} = \frac{72000000}{16 \times 250000} = 18
$$

也是整数。而 **57600bps** 就麻烦了：

$$
\text{USARTDIV} = \frac{72000000}{16 \times 57600} = 78.125
$$

0.125 可以精确表示。真正出现误差的是这种：`f_PCLK = 8MHz`（用内部 HSI 时）配 115200：

$$
\text{USARTDIV} = \frac{8000000}{16 \times 115200} = 4.34
$$

小数部分 0.34 只能近似到 0.3125 或 0.375，实际波特率偏离理论值约 **1.5%**。

**UART 的误差容忍度是多少？** 异步通信靠每帧起始位重新同步，误差会在一帧内累积。接收方在每位的中间采样，10 位一帧累积误差不能超过半位，所以理论极限是 5%，但工程上要求 **< 2%**，超过 3% 就开始偶发乱码。

**结论：一定要用外部晶振（HSE）而不是内部 RC（HSI）。** HSI 的标称精度是 ±1%，加上温度漂移可达 ±3%，叠上分频误差直接超限。用 HSE 8MHz 晶振（±20ppm）配 PLL 到 72MHz，误差几乎为零。

## 5.3 三种收发方式

### 轮询（阻塞）

```c
HAL_UART_Transmit(&huart1, (uint8_t *)"hello\r\n", 7, 100);
```

简单可靠，但发送期间 CPU 全程等待。115200bps 下发 100 字节约 8.7ms，这期间什么都干不了。只适合调试打印、初始化阶段。

### 中断

发送/接收由中断驱动，CPU 只在字节到达时进入 ISR。适合低速、不定时的数据。

### DMA

DMA 直接在外设和内存之间搬数据，CPU 完全不参与。适合大批量、高速率传输（比如刷屏、传文件）。

**最实用的组合是：发送用 DMA，接收用 DMA + 空闲中断。**

## 5.4 接收不定长数据：空闲中断 + DMA

这是工程中最常用的方案。思路：

1. DMA 以循环模式持续把串口数据搬进缓冲区
2. 利用串口的 **IDLE（空闲）中断**——当总线连续一个字节时间没有新数据时触发
3. 在 IDLE 中断里计算 DMA 已经搬了多少字节，这就是这一帧的长度
4. 处理完重新启动 DMA

```c
#define RX_BUF_SIZE 256
uint8_t  rx_buf[RX_BUF_SIZE];
volatile uint16_t rx_len = 0;
volatile uint8_t  rx_flag = 0;

/* 初始化时启动 */
HAL_UARTEx_ReceiveToIdle_DMA(&huart1, rx_buf, RX_BUF_SIZE);

/* 回调：HAL 检测到 IDLE 后调用，Size 是本帧长度 */
void HAL_UARTEx_RxEventCallback(UART_HandleTypeDef *huart, uint16_t Size)
{
    if (huart->Instance == USART1) {
        rx_len  = Size;
        rx_flag = 1;                       /* 只置标志，不在中断里解析 */
        HAL_UARTEx_ReceiveToIdle_DMA(huart, rx_buf, RX_BUF_SIZE);  /* 重新挂上 */
    }
}

/* 主循环里处理 */
if (rx_flag) {
    rx_flag = 0;
    ParseFrame(rx_buf, rx_len);
}
```

这个方案的优点：**不定长、零丢包、CPU 占用极低**，比自己管理环形缓冲简单得多。

如果 HAL 版本较老不支持 `ReceiveToIdle`，可以手动使能 IDLE 中断并在 `USART1_IRQHandler` 里判断 `__HAL_UART_GET_FLAG(huart, UART_FLAG_IDLE)`。

## 5.5 printf 重定向

调试时最方便的还是 `printf`。重定向的原理是：标准库的 `printf` 最终会调用一个底层字符输出函数，把这个函数改成"往串口写一个字节"即可。

### 方法一：重写 fputc（Keil / ARMCC）

```c
#include <stdio.h>

int fputc(int ch, FILE *f)
{
    HAL_UART_Transmit(&huart1, (uint8_t *)&ch, 1, 10);
    return ch;
}
```

在 Keil 里还需要勾选 **Use MicroLIB**，否则会因为半主机（semihosting）机制导致程序卡在 `printf` 里。

### 方法二：重写 _write（GCC / arm-none-eabi）

```c
int _write(int fd, char *ptr, int len)
{
    HAL_UART_Transmit(&huart1, (uint8_t *)ptr, len, 100);
    return len;
}
```

GCC 工具链用 `_write`，不需要 MicroLIB。

### 方法三：不用标准库，自己实现（推荐用于正式产品）

标准库的 `printf` 会链接进几十 KB 的代码（浮点格式化尤其庞大），对 Flash 只有 64KB 的 F103C8 来说是巨大浪费。更实际的做法是写一个精简版：

```c
void uart_printf(const char *fmt, ...)
{
    char buf[128];
    va_list ap;
    va_start(ap, fmt);
    int n = vsnprintf(buf, sizeof(buf), fmt, ap);
    va_end(ap);
    if (n > 0) HAL_UART_Transmit_DMA(&huart1, (uint8_t *)buf, n);
}
```

用 `vsnprintf` 而非 `printf`，格式化到内存再一次性 DMA 发出去。这样既不阻塞，也能控制缓冲区大小。

**注意 `uart_printf` 不可重入。** 如果主循环和中断都调用它，`buf` 会被覆盖。加一个忙标志或者用独立缓冲区。

## 5.6 一个字节出错就永久卡死：ORE 问题

这是 STM32 串口最著名的坑。

**现象**：程序跑了几分钟或几小时后，串口突然不再接收任何数据，重启才好。

**原因**：接收数据寄存器（RDR）里的数据还没被读走，下一个字节就到了，触发**溢出错误（ORE）**。在 ORE 置位状态下，HAL 库会停止接收，因为状态机认为"数据已经不可信"。如果没写错误回调，这个状态会一直保持。

**解决**：

```c
void HAL_UART_ErrorCallback(UART_HandleTypeDef *huart)
{
    if (huart->ErrorCode & HAL_UART_ERROR_ORE) {
        /* 清标志并重新启动接收 */
        __HAL_UART_CLEAR_OREFLAG(huart);
        HAL_UART_Receive_IT(huart, &rx_byte, 1);
    }
}
```

更根本的对策是**别让它溢出**：用 DMA 接收（硬件搬运，不会因为软件慢而丢），或者提高接收中断的优先级。

## 5.7 五个接线与配置故障

**故障一：TX 接 TX、RX 接 RX。**
串口是交叉连接：A 的 TX 接 B 的 RX。接错了完全没反应，而且不会有任何报错。这是最高频的低级错误，排查时第一个怀疑它。

**故障二：没有共地。**
两块板子只接了 TX/RX 没接 GND。信号是相对电平，没有共同参考点就无法判断高低。表现是乱码或者完全无数据。**任何通信都必须先共地。**

**故障三：TTL 直接连 RS232。**
STM32 输出的是 0/3.3V 的 TTL 电平，而 RS232 是 ±12V 且逻辑反相。直接连会烧毁串口甚至芯片，必须经过 MAX3232 之类的电平转换。

**故障四：波特率对但校验/停止位不对。**
8N1 连 8E1，能收到数据但全是乱码，因为帧边界错位。用逻辑分析仪看波形能立刻发现。

**故障五：调试口和串口复用。**
有些开发板把 USART1 接到了 CH340 下载芯片，同时也连到排针。两处同时使用会互相干扰。

## 5.8 本章小结

- 帧格式优先用 8N1；波特率误差要控制在 2% 以内，必须用外部晶振。
- 72MHz 配 115200 / 9600 误差为零，是"安全频点"。
- 接收不定长数据用 **DMA + IDLE 空闲中断**，不要用轮询或逐字节中断。
- `printf` 重定向在 Keil 里重写 `fputc` + 勾选 MicroLIB，GCC 里重写 `_write`。
- 正式产品建议用 `vsnprintf` 自建精简打印，省 Flash 且不阻塞。
- 串口"用一会儿就死"几乎都是 ORE 溢出，必须写错误回调恢复。
- 接线记住三条：交叉连、必须共地、TTL 不能直连 RS232。
