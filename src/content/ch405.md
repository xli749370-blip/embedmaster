# 第五章 模块化：把能跑的单文件拆成能维护的工程

> 前四章解决"代码对不对"。这一章解决"半年后还改不改得动"。嵌入式工程里最典型的失败不是写不出功能，而是第一个功能写完就开始堆，堆到 800 行的 `main.c`，加任何功能都要先读半小时。

## 5.1 一个模块的最小闭环

模块 = 一个 `.c` + 一个 `.h`。`.c` 放实现，`.h` 放"别人需要知道的全部信息"。这个界限划清了，模块就自然独立了：

```c
/* led.h —— 对外契约：只暴露别人必须知道的 */
#ifndef LED_H
#define LED_H

#include <stdint.h>

typedef enum {
    LED_RED = 0,
    LED_GREEN,
    LED_COUNT
} LedId;

void    led_init(void);
void    led_on(LedId id);
void    led_off(LedId id);
void    led_toggle(LedId id);

#endif /* LED_H */
```

```c
/* led.c —— 实现细节全藏在这里 */
#include "led.h"
#include "board_gpio.h"

/* static：这些符号不出这个文件，其他模块看不到也引用不到 */
static const uint16_t s_pin_map[LED_COUNT] = { 0, 1 };

void led_init(void)
{
    for (int i = 0; i < LED_COUNT; i++) {
        board_gpio_config_output(s_pin_map[i]);
        board_gpio_write(s_pin_map[i], 0);
    }
}

void led_on(LedId id)
{
    if (id >= LED_COUNT) return;    /* 边界检查，防上层传错 */
    board_gpio_write(s_pin_map[id], 1);
}
```

三个要点：

- **`.h` 里没有 `uint16_t s_pin_map`**。这是实现细节，暴露出去别人就会依赖，将来想改成结构体数组就得改所有调用方
- **`s_` 前缀 + `static`**。两者都是约定，但 `static` 是强制的（不加就进了全局符号表，可能撞名）
- **函数里检查参数边界**。模块是对外承诺，不能假设调用方永远正确

## 5.2 头文件的四条规则

### 规则一：必须有包含守卫

```c
#ifndef LED_H
#define LED_H
/* ... */
#endif
```

或者 `#pragma once`（GCC/Keil 都支持，但标准写法更保险）。没有守卫时，两个 `.c` 都 `#include "led.h"` 会重复定义，报一堆错。

### 规则二：只放声明，不放定义

```c
/* 错误：这是定义，每个包含它的 .c 都会生成一份 → 链接时重复符号 */
uint32_t g_tick;

/* 正确：这是声明，告诉编译器"有这个东西，定义在别处" */
extern uint32_t g_tick;

/* 例外：inline 函数和宏可以放头文件 */
static inline uint32_t min_u32(uint32_t a, uint32_t b) { return a < b ? a : b; }
```

`static inline` 是唯一"能在头文件里定义函数"的合法形式——`static` 让每个 `.c` 各有一份副本，`inline` 提示内联，不产生外部符号冲突。这是 CMSIS 里的 `__STATIC_INLINE` 的来源。

### 规则三：不在头文件里包含无关的头

头文件包含会传染。`a.h` 包含了 `stm32f1xx_hal.h`，所有包含 `a.h` 的文件都要编译整个 HAL——编译时间会指数级增长。

更好的做法是**前向声明**：

```c
/* 我只需要"存在一个叫 Frame 的结构体"，不需要知道它长什么样 */
struct Frame;
void frame_send(const struct Frame *f);
```

只有当需要 `sizeof` 或者访问成员时，才必须包含完整定义。

### 规则四：头文件要能独立编译

测试方法：新建一个 `.c`，内容只有 `#include "led.h"`，能编译通过才算合格。不能通过说明它依赖了别人先包含某个头——这种隐式依赖会让代码顺序敏感，改个包含顺序就编译失败。

## 5.3 依赖方向必须单向

这是模块化最重要的架构约束。分层的依赖只能**从上往下**，不能反向，也不能横向纠缠：

```
   app/          业务逻辑（状态机、控制算法）
     ↓
   drivers/      器件驱动（led、按键、传感器）
     ↓
   board/        板级定义（哪个引脚接了什么）
     ↓
   hal/          STM32 HAL / 寄存器
```

**为什么不能让 `drivers/` 反过来调 `app/`？** 因为那样 `led.c` 就依赖了业务逻辑，想把这个驱动复用到另一个项目就得连业务代码一起搬。反过来，`app` 依赖 `drivers` 是自然的——上层知道下层，下层不知道上层。

需要"下层通知上层"时，用**回调**（下一节），而不是让下层直接 include 上层的头文件。

## 5.4 不透明指针：把结构体藏起来

如果模块内部有一个复杂的状态结构体，把它放进 `.h` 就等于把内部结构公开了。做法是只在 `.h` 里声明"有这么个类型"，在 `.c` 里定义它的内容：

```c
/* uart.h —— 调用方只知道有个 Uart 类型，不知道里面有什么 */
typedef struct Uart Uart;      /* 不完整类型 */

Uart *uart_create(uint32_t baudrate);
void  uart_destroy(Uart *u);
int   uart_write(Uart *u, const uint8_t *data, uint32_t len);
```

```c
/* uart.c —— 真实结构只在这里可见 */
struct Uart {
    uint32_t baud;
    uint8_t  rx_buf[128];
    volatile uint16_t head;
    volatile uint16_t tail;
    /* 想加字段随便加，不影响任何调用方 */
};

Uart *uart_create(uint32_t baudrate) { /* ... */ }
```

收益很明确：**内部结构完全自由演化**。今天加一个 `dma_handle` 字段，所有调用方一行都不用改——因为它们从来没见过这个结构体的定义。这就是 HAL 库把 `UART_HandleTypeDef` 完整暴露出来、导致你改个库版本就得改代码的反面。

代价是：调用方不能自己 `Uart u;` 在栈上分配，必须用 `uart_create` 走堆或者静态池。在资源受限的 MCU 上，可以用"静态池 + 句柄索引"替代真正的动态分配：

```c
/* 不用 malloc，用固定池，create 只是从池里取一个 */
static struct Uart s_pool[2];
static uint8_t s_used[2];

Uart *uart_create(uint32_t baudrate)
{
    for (int i = 0; i < 2; i++) {
        if (!s_used[i]) { s_used[i] = 1; return &s_pool[i]; }
    }
    return NULL;    /* 池满了 */
}
```

## 5.5 函数指针：让下层能通知上层

函数指针在嵌入式里的三大用途：回调、命令表、状态机跳转表。

### 回调注册

```c
/* button.h */
typedef void (*ButtonCallback)(uint8_t id, uint8_t pressed);

void button_register_callback(ButtonCallback cb);
```

```c
/* button.c —— 底层只管检测，出事就喊一声，不关心谁在处理 */
static ButtonCallback s_cb = NULL;

void button_register_callback(ButtonCallback cb) { s_cb = cb; }

void button_scan(void)
{
    if (pressed && s_cb) s_cb(0, 1);   /* 判空再调，没注册就跳过 */
}
```

```c
/* app.c —— 上层注册自己的处理函数 */
static void on_button(uint8_t id, uint8_t pressed)
{
    if (pressed) ui_next_page();
}

void app_init(void) { button_register_callback(on_button); }
```

依赖方向保持单向：`button.c` 完全不知道 `app.c` 的存在。

回调的三条纪律：

1. **调用前判空**。`s_cb` 可能是 `NULL`，直接调就是 HardFault
2. **不在 ISR 里做重活**。回调常在中断上下文执行，注册时要想清楚这一点
3. **不要在回调里注销自己**。会释放掉正在执行的函数所在的模块，行为未定义

### 命令表

串口命令行、菜单系统用表驱动比 `if-else` 链优雅得多：

```c
typedef struct {
    const char *name;
    void (*handler)(int argc, char **argv);
    const char *help;
} Cmd;

static const Cmd s_cmds[] = {
    { "help",  cmd_help,  "列出所有命令" },
    { "reset", cmd_reset, "软件复位" },
    { "info",  cmd_info,  "打印固件版本" },
};
```

加命令只需往表里加一行，分发逻辑一行都不用改。这就是"开闭原则"在 C 里的样子。

## 5.6 状态机：把 if-else 森林变成表

嵌入式里有大量"现在处于什么状态、收到什么事件、该做什么"的逻辑。最常见的写法是嵌套 `switch`，写着写着就变成几百行。

```c
/* 反例：随状态和事件增长而爆炸 */
if (state == IDLE) {
    if (evt == START) { ... }
    else if (evt == TIMEOUT) { ... }
} else if (state == RUN) { ... }
```

改用**状态转移表**，逻辑和数据结构分离：

```c
typedef enum { ST_IDLE, ST_RUN, ST_FAULT, ST_COUNT } State;
typedef enum { EV_START, EV_STOP, EV_ERROR, EV_RESET, EV_COUNT } Event;

typedef struct {
    State  next;                 /* 目标状态 */
    void (*action)(void);        /* 转移时执行的动作，NULL 表示无动作 */
} Transition;

/* 行 = 当前状态，列 = 事件；全部用设计指定值初始化，没写到的默认 0 */
static const Transition s_table[ST_COUNT][EV_COUNT] = {
    [ST_IDLE]  = { [EV_START] = { ST_RUN,   on_start },
                   [EV_ERROR] = { ST_FAULT, on_fault } },
    [ST_RUN]   = { [EV_STOP]  = { ST_IDLE,  on_stop  },
                   [EV_ERROR] = { ST_FAULT, on_fault } },
    [ST_FAULT] = { [EV_RESET] = { ST_IDLE,  on_reset } },
};

static State s_state = ST_IDLE;

void fsm_dispatch(Event evt)
{
    if (evt >= EV_COUNT) return;
    const Transition t = s_table[s_state][evt];
    if (t.next == 0 && t.action == NULL) return;   /* 该状态下不响应这个事件 */
    if (t.action) t.action();
    s_state = t.next;
}
```

好处：

- **新增状态/事件是加数据，不是改逻辑**，改错的概率大幅下降
- **整张表一眼看全**，能直接对着需求文档核对，发现"这个状态漏了处理"
- **可测试**。`fsm_dispatch` 是纯函数（除了改 `s_state`），喂事件序列就能验证

这里用了 C99 的指定初始化器 `[ST_IDLE] = {...}`，可读性远好于按位置初始化——而且状态枚举加一个成员时，表不会整体错位。

## 5.7 错误码：返回值要能区分"为什么失败"

裸返回 `0/-1` 的信息量太低。定义一套项目内的错误码，让调用方能分类处理：

```c
typedef enum {
    ERR_OK        = 0,
    ERR_PARAM     = 1,    /* 参数非法，调用方的错，重试没用 */
    ERR_TIMEOUT   = 2,    /* 超时，可能重试能成功 */
    ERR_BUSY      = 3,    /* 忙，稍后重试 */
    ERR_NO_MEM    = 4,    /* 资源不足 */
    ERR_HW        = 5,    /* 硬件故障，需要上报 */
} ErrCode;
```

约定：**所有可能失败的函数都返回 `ErrCode`，业务数据用出参带回**。

```c
ErrCode sensor_read(int16_t *out_temp)
{
    if (out_temp == NULL) return ERR_PARAM;
    if (!i2c_ready())     return ERR_BUSY;
    *out_temp = read_reg(TEMP_REG);
    return ERR_OK;
}
```

这样调用方写出来是自解释的：

```c
int16_t t;
switch (sensor_read(&t)) {
    case ERR_OK:      show_temp(t);      break;
    case ERR_BUSY:    /* 下个周期再试，不报错 */  break;
    case ERR_TIMEOUT: log_warn("sensor to");      break;
    default:          enter_safe_state();         break;
}
```

比 `if (ret < 0) { /* 到底哪错了 */ }` 强太多。

## 5.8 别在主逻辑里直接调 HAL

这是最常见的一条工程建议，也是最容易被忽略的：

```c
/* 反面：业务逻辑和具体引脚绑死 */
void app_update(void)
{
    if (over_temp) {
        HAL_GPIO_WritePin(GPIOA, GPIO_PIN_5, GPIO_PIN_SET);   /* 风扇 */
    }
}
```

问题：换板子（引脚变了）要改业务代码；想在没有硬件的 PC 上跑单元测试，`HAL_GPIO_WritePin` 链接不过。

抽一层：

```c
/* board.h —— 板级抽象，只说"做什么"，不说"怎么接" */
void board_fan_set(int on);
int  board_btn_read(void);
```

```c
/* board.c —— 唯一知道引脚号的地方 */
void board_fan_set(int on)
{
    HAL_GPIO_WritePin(GPIOA, GPIO_PIN_5, on ? GPIO_PIN_SET : GPIO_PIN_RESET);
}
```

```c
/* app.c —— 干净的业务逻辑 */
void app_update(void)
{
    if (over_temp) board_fan_set(1);
}
```

现在换板子只改 `board.c` 一个文件；在 PC 上测试时，给 `board.c` 写一个假实现（stub）就行，业务代码一行不动。

## 5.9 命名与文件组织的约定

不用纠结具体风格，**关键是全项目统一**。下面是嵌入式里最常见的一套：

| 对象 | 约定 | 例子 |
|---|---|---|
| 文件名 | 全小写 + 下划线 | `board_gpio.c` |
| 模块私有变量 | `s_` 前缀 + `static` | `static uint8_t s_inited` |
| 全局变量 | `g_` 前缀 | `uint32_t g_tick` |
| 宏/常量 | 全大写 | `LED_COUNT`、`UART_BAUD` |
| 类型 | 大驼峰 + `_t` | `UartHandle_t` |
| 函数 | 模块名_动作 | `led_init()`、`uart_write()` |
| 枚举成员 | 全大写 + 模块前缀 | `LED_RED`、`ST_IDLE` |

`g_` / `s_` 前缀的价值不是好看，而是**看代码时立刻知道这个变量的生命周期和可见范围**。一个 `s_` 开头的变量突然在别的文件里出现，一眼就是错的。

## 5.10 这一章要带走的东西

1. 模块 = `.c` + `.h`，`.h` 只放"别人必须知道的"，实现细节留在 `.c`
2. 头文件四规则：包含守卫、只放声明、少包含、能独立编译
3. 依赖方向单向：`app → drivers → board → hal`，下层通知上层用回调
4. `static` 是模块私有的强制手段，`s_`/`g_` 前缀是它的可读标记
5. 不透明指针让内部结构自由演化，MCU 上用静态池替代 `malloc`
6. 回调前必须判空，回调里不做重活
7. 命令表、状态转移表把"逻辑爆炸"变成"数据增长"
8. 返回 `ErrCode` 而不是 `0/-1`，业务数据走出参
9. 业务逻辑不直接调 HAL，中间加一层 `board_`

写到这里，从指针到模块化的链路是完整的了：**指针解决寻址，位操作解决寄存器，关键字解决内存布局与可见性，并发解决中断与主循环的协作，模块化解决长期维护**。这套东西在 STM32 上跑通之后，换成任何 MCU 都只是换寄存器地址和库函数名。

接下来最值得练的不是再学一个外设，而是把这五章的东西用在一个真实项目上——比如一个按键 + LED + 串口命令 + 状态机的完整小系统，二十行一个模块，五个文件讲清楚。
