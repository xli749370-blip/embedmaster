# 第七章 DMA 双缓冲与半传输中断

> 上一章的 SPI+DMA 里，我们让 DMA 一次搬完 8 个字节就收工。真实系统不是这样：ADC 每秒采一万次、串口每秒进来上千字节，DMA 是**永远不休息**的。于是新的问题出现了——DMA 正在往某个数组里写的时候，CPU 能不能读它？
>
> 不能。这就是这一章要解决的问题。

## 7.1 单缓冲的尴尬：一块内存，两拨人抢

先回到最基本的单缓冲模型：一个数组 `buf[64]`，DMA 从 `ADC->DR` 往里搬，搬满 64 个就触发一次传输完成中断，CPU 在中断里处理这 64 个数据。

看起来没问题，但把时间轴摊开就露馅了：

```
DMA  : [==== 填 buf ====][ 停 ][==== 填 buf ====][ 停 ]
CPU  : [      闲         ][处理][      闲         ][处理]
              ↑ 这段时间 CPU 什么也干不了
```

**DMA 填的时候 CPU 只能等，CPU 处理的时候 DMA 只能停。** 两者严格串行，系统吞吐 = 填一块的时间 + 处理一块的时间。

算个数。ADC 采样率 $f_s = 10\ \text{kHz}$，块长 $N = 64$，那么填满一块需要：

$$
T_{fill} = \frac{N}{f_s} = \frac{64}{10000} = 6.4\ \text{ms}
$$

如果 CPU 处理这 64 个点（比如做一次 FIR 滤波）需要 $T_{cpu} = 5\ \text{ms}$，单缓冲的实际块周期就是：

$$
T_{block} = T_{fill} + T_{cpu} = 6.4 + 5 = 11.4\ \text{ms}
$$

而 ADC 在这 11.4 ms 里产出了 $11.4 \times 10 = 114$ 个样本，缓冲区只装得下 64 个。**丢掉的那 50 个样本就是你听到的杂音、看到的波形断裂。**

要救回来，只能把 $N$ 加大。但 $N$ 加大意味着延迟变大，实时性变差。**单缓冲的死结：吞吐和延迟互相拉扯，没有解。**

## 7.2 双缓冲：把一块地分成两块

解法的思路很朴素：**别让两拨人抢同一块地，给他们各分一块。**

```
buf A : [== DMA 填 ==][ CPU 处理 ][== DMA 填 ==]
buf B : [ CPU 处理 ][== DMA 填 ==][ CPU 处理 ]
```

任何时刻，DMA 在填其中一块，CPU 在处理另一块。等 DMA 填满了 A，它自动转到 B，同时把 A「交」给 CPU。等 B 填满，再转回 A。

两个指针来回交替，像打乒乓球一样——所以叫**乒乓缓冲（ping-pong buffer）**。

```c
#define BUF_LEN 64
static uint16_t adc_buf[2][BUF_LEN];   // 两块，不是一块的两倍长度

/* 关键：CNDTR 填的是「一块」的长度，不是总长度 */
HAL_DMAEx_MultiBufferStart_IT(&hdma_adc,
                              (uint32_t)&ADC1->DR,
                              (uint32_t)adc_buf[0],   // M0AR
                              (uint32_t)adc_buf[1],   // M1AR
                              BUF_LEN);
HAL_ADC_Start(&hadc1);
```

注意这里的 CNDTR 是 **`BUF_LEN` 而不是 `BUF_LEN * 2`**。在双缓冲模式下，CNDTR 计的是「当前这一块」的进度，搬满一块就自动切到另一块并把 CNDTR 重装。这一点是新手最容易搞错的——填了两倍长度，结果只搬了半块就切走。

动画里盯住两个细节：

1. **前 4 拍 CPU 一直是「空闲」**。这不是 bug——第一块没填满之前，CPU 手里根本没有数据可处理。这叫**首块延迟**，双缓冲也躲不掉。
2. **第 4 拍之后，每一拍 DMA 和 CPU 都在动**，重叠率爬到 100%。对比最下面那行灰色的「单缓冲」——它永远是一格隔一格。

### 吞吐变成了多少

双缓冲下，一个块周期取两者中较慢的那个：

$$
T_{block} = \max\left(T_{fill},\ T_{cpu}\right) = \max(6.4,\ 5) = 6.4\ \text{ms}
$$

对比单缓冲的 11.4 ms，**吞吐提升了 78%**。更关键的是：只要满足

$$
T_{cpu} \le T_{fill}
$$

系统就不会丢样本。这条不等式是判断「要不要上双缓冲」的唯一标准——**先算 $T_{cpu}$ 和 $T_{fill}$，再决定架构**，不要凭感觉堆缓冲。

如果 $T_{cpu} > T_{fill}$，双缓冲也救不了你，那是算力不够，得降采样率、换算法或者上 FPU/DSP 指令。

### 顺带解决的两个问题

双缓冲不只是提速，它还顺手解决了两个隐蔽故障：

| 问题 | 单缓冲下的表现 | 双缓冲下为什么好了 |
| --- | --- | --- |
| 撕裂（tearing） | CPU 读到一半的数据被 DMA 覆盖，波形里出现单个跳变的坏点 | CPU 读的那块 DMA 不会碰，物理上不可能被覆盖 |
| 中断关太久 | 处理大块数据要关中断，抖动变大 | 可以只关「切换指针」那几行，数据处理放中断外 |
| 数据拷贝 | 中断里 memcpy 到处理区，多一次搬运 | 零拷贝，指针直接指过去 |

**第二条尤其重要**：很多人以为双缓冲就是为了快，其实它最大的价值是**让中断变短**。中断里只做「记下一个指针、发一个信号量」，真正的处理放到任务里做——这正是后面 RTOS 课程里那个经典模式的雏形。

## 7.3 半传输中断：把「等满」改成「等半」

双缓冲解决了吞吐，但没解决**延迟**。

设想一个音频应用：块长 64，采样率 10 kHz，一块 6.4 ms。用户在麦克风前拍一下手，这个声音要先攒满 64 个样本才能被处理，也就是说**声音延迟至少 6.4 ms**。加上 DAC 输出端的缓冲，端到端延迟可能到 15 ms 以上，开会时能明显感觉到回声。

DMA 提供了一个额外的中断源专门治这个：**半传输（Half Transfer，HT）**。

```
CNDTR : 64 → 48 → 32 → 16 → 0 → 重装 64
                ↑            ↑
             HT 置位       TC 置位
```

搬完一半（CNDTR 从 64 走到 32）时，HT 标志置位，产生中断；搬完整块，TC 置位。

有两种用法：

**用法一：处理提前开始。** 在 HT 中断里先处理前一半，在 TC 中断里处理后半段。延迟从 $N/f_s$ 降到 $N/(2f_s)$——上面那个例子里从 6.4 ms 降到 3.2 ms，砍一半。

**用法二：环形缓冲的读写指针。** 这是串口收不定长数据最常用的套路，本质上是把单块缓冲区当成首尾相接的环：

```c
/* 经典写法：CNDTR = 总长，HT 处理前半，TC 处理后半 */
HAL_UART_Receive_DMA(&huart1, ring, RING_LEN);   // RING_LEN = 256

void HAL_UART_RxHalfCpltCallback(UART_HandleTypeDef *huart)
{
    /* ring[0..127] 已满，可以安全读取 */
    ring_push(ring, RING_LEN / 2);
}

void HAL_UART_RxCpltCallback(UART_HandleTypeDef *huart)
{
    /* ring[128..255] 已满 */
    ring_push(ring + RING_LEN / 2, RING_LEN / 2);
}
```

注意这里的 CNDTR 是 `RING_LEN`（总长），不是半长——和双缓冲模式正好相反。**两套机制长得像，含义完全不同**，配错了表现都一样：数据少一半，或者全是旧数据。

### 双缓冲 + HT 一起用

STM32 的 DBM（Double Buffer Mode）位打开后，HT 的含义变成**「当前这一块的半块」**。这时你可以做四段流水：

| 时刻 | DMA 动作 | CPU 动作 |
| --- | --- | --- |
| A 半满（HT） | 继续填 A 的后半 | 处理 A 的前半 |
| A 满（TC） | 切到 B，开始填 B | 处理 A 的后半 |
| B 半满（HT） | 继续填 B 的后半 | 处理 B 的前半 |
| B 满（TC） | 切回 A | 处理 B 的后半 |

延迟再砍一半，代价是中断频率翻倍。**中断越频繁，CPU 花在进出中断上的开销越大**——这是所有实时系统里永恒的交易。

## 7.4 三种缓冲策略怎么选

不要一上来就上双缓冲。先把下面这张表看完：

| 策略 | 中断频率 | 延迟 | CPU 占用 | 适用场景 |
| --- | --- | --- | --- | --- |
| 单缓冲 | 每块 1 次（TC） | 1 块 | 高（串行等） | 低速、非实时：电池电压、温度（1 Hz 级） |
| 双缓冲 | 每块 1 次（TC） | 1 块 | 低（重叠） | 中高速、要求不丢数：ADC 波形、音频采集 |
| 双缓冲 + HT | 每块 2 次 | 半块 | 最低（重叠 + 早启动） | 低延迟要求：音频回环、电机电流环 |
| 环形缓冲（单块 + HT/TC） | 每半块 1 次 | 半块 | 低 | 不定长串口数据、日志流 |

一句话判据：**先看 $T_{cpu}$ 和 $T_{fill}$ 的比值，再看延迟要求。**

- $T_{cpu} < T_{fill}$ 且延迟不敏感 → 单缓冲够用，别复杂化；
- $T_{cpu}$ 接近或超过 $T_{fill}$ → 必须双缓冲；
- 延迟是硬指标（音频、控制环）→ 再加 HT。

## 7.5 五个必踩的坑

**坑一：CNDTR 填成总长度。**
双缓冲模式下 CNDTR 是「一块」的长度。填成 `2 * BUF_LEN`，DMA 会以为一块就有两倍长，实际只搬了半块就切走，另一半永远是旧数据。**判据：切换后立刻看另一块数组的前几个元素，如果和第 0 次采样一模一样，就是这个问题。**

**坑二：在 TC 中断里处理「刚填满」的那块，但取错了指针。**
TC 触发时，DMA 已经切到下一块了，`CMAR` 指向的是**正在被写的新块**，不是刚填满的旧块。直接读 `CMAR` 指向的地址，读到的是一半新一半旧的数据。正确做法是用一个软标志记录「上一块是哪块」，或者干脆用回调里的 `hadc->Instance` 分区判断。

**坑三：处理时间超过块时间还怪 DMA 丢数。**
$T_{cpu} > T_{fill}$ 时，双缓冲只能扛一个块周期。第二块填满时 CPU 还没处理完第一块，DMA 就会覆盖。表现出来是「偶发」的数据错乱，很难查。**必须在开发期把 $T_{cpu}$ 实测出来**（用一个 GPIO 翻转 + 示波器，或者 DWT 周期计数器），不能拍脑袋估。

**坑四：缓存一致性（M7/H7 才有）。**
带 D-Cache 的芯片上，DMA 写进内存的数据可能还在 Cache 里没落到 SRAM，CPU 读到的就是旧值。必须在处理前 `SCB_InvalidateDCache_by_Addr()`，在交给 DMA 前 `SCB_CleanDCache_by_Addr()`。F1/F4 没有 D-Cache，不用管——但换芯片时这条会要命。

**坑五：用 volatile 代替内存屏障。**
`volatile` 只保证「每次都从内存读」，不保证编译器和 CPU 不重排。双缓冲切换指针这种跨上下文共享的变量，要么用 `__DMB()`，要么放在临界区里改。**只加 volatile 在 -O2 下依然会出现「指针切换了但数据处理了」的乱序。**

## 7.6 本章小结

- 单缓冲的根因是「一块内存两拨人抢」，表现为 DMA 与 CPU 严格串行，吞吐 = 填 + 算。
- 双缓冲给两拨人各分一块地，块周期从 $T_{fill} + T_{cpu}$ 降到 $\max(T_{fill}, T_{cpu})$。
- 判据只有一条：$T_{cpu} \le T_{fill}$。不满足就要降速或换算法，加缓冲没用。
- 双缓冲更大的价值是**让中断变短**：中断里只切指针、发信号量，处理搬到任务里做。
- HT 把延迟从一块降到半块，代价是中断频率翻倍；环形缓冲用同一套机制收不定长数据。
- 五个坑：CNDTR 填总长、TC 里取错指针、算不完还加缓冲、D-Cache 不一致、volatile 当屏障。

## 结语：从会写代码到会做系统

这七章串起来是一条完整的链：

**GPIO** 让你控制引脚 → **中断**让你及时响应 → **定时器**让你产生精确的时间与波形 → **ADC** 让你感知模拟世界 → **串口**让你看见内部状态 → **总线**让你接入更多器件 → **DMA** 让你把这些数据搬得又快又稳，而不必让 CPU 亲自搬砖。

再往上就是把这些能力组合成一个系统：用定时器驱动姿态环、用 ADC 采传感器、用串口和上位机通信、用 I2C 读 IMU。这时候新的问题会出现——多任务的时序竞争、内存的紧张、实时性的保证。那是 RTOS 和系统设计的领域，也是下一个阶段要解决的问题。
