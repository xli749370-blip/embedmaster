## 3.1 为什么切换必须「保存现场」

CPU 的寄存器只有一套——R0~R12、SP、LR、PC、xPSR 是**全局唯一**的硬件资源。当任务 A 正在跑，它的局部变量地址、循环计数、返回地址全在这套寄存器里。如果此时直接跳去跑任务 B，B 会毫无顾忌地覆盖掉 R0、LR、PC……等 A 再回来时，它的世界已经面目全非，程序必然跑飞。

所以「上下文切换」的本质就是：**在离开一个任务前，把这套寄存器的值存起来；在回到一个任务时，再把值原样装回去。** 存到哪？存到**这个任务自己的栈**里。

## 3.2 上下文到底是什么

所谓「上下文（Context）」，就是能让一个任务「暂停后还能原样续上」所需的全部寄存器。在 Cortex-M 上，一次 PendSV 切换会处理的至少包括：

- **通用寄存器 R0~R12**：普通计算与传参；
- **R13 / SP**：栈指针，指向当前任务的栈顶（切换就是换 SP）；
- **R14 / LR**：链接寄存器，返回地址；
- **R15 / PC**：程序计数器，下一条要执行的指令；
- **xPSR**：程序状态字（含条件标志位）；
- 如果打开了 FPU，还有 **S0~S15 / FPSCR**（惰性入栈，懒到真正用到浮点才存）。

这些寄存器被整整齐齐压入当前任务的栈，形成一个「上下文帧」。谁先压、谁后压由芯片 ABI 约定，恢复时反序弹出即可。

## 3.3 两种触发切换的时机

切换只发生在「调度器有机会运行时」。常见两类时机：

**① 系统节拍（SysTick）中断。** 每 1ms（一个 tick）来一次，此时代码检查：当前任务的时间片用完了吗？有没有更高优先级任务就绪了？如果有，就请求一次切换。这是「时间驱动」的调度。

**② 任务主动让出 / 阻塞。** 任务调用 `vTaskDelay(100)`、`xQueueReceive` 没等到数据、`xSemaphoreTake` 没抢到锁，都会主动进入阻塞态并触发切换——把 CPU 让给别人。这是「事件驱动」的调度，效率更高（不需要等 tick）。

无论哪种，FreeRTOS 都不会在任意位置硬切，而是统一延后到 **PendSV 异常**里做。为什么？因为 PendSV 可以被「挂起」——如果此刻正有更高优先级的中断在跑，PendSV 会等它结束再执行，从而保证**切换不会打断真正紧急的中断**。这是 Cortex-M 上 RTOS 切换的标准姿势。

## 3.4 切换的精确步骤

把一次「从任务 A 切到任务 B」拆开看：

1. 触发点（tick 或阻塞调用）调用 `portYIELD()`，置位一个「该切了」的标志（PendSV 待处理位）；
2. 当前指令流走到异常边界，硬件先把**部分**寄存器自动压入 A 的栈（Cortex-M 进异常自动压 R0~R3、R12、LR、PC、xPSR）；
3. 进入 PendSV 处理函数，软件把**剩下**的寄存器（R4~R11 等）也压入 A 的栈；
4. 把 A 的栈顶指针（SP）保存到 **A 的 TCB**；
5. 从 **B 的 TCB** 取出 B 的栈顶指针，赋给 SP；
6. 软件弹出 B 剩下的寄存器，硬件再自动弹出 B 的寄存器，最后跳到 B 暂停处的下一条指令。

整个过程是**对称的**——进出对称、压弹对称。切换完成后，B 完全不知道自己曾被「冻」了多久，继续往下跑。

## 3.5 任务栈：每个任务的「独立桌面」

把栈想象成每个任务专属的办公桌。任务运行时，它的局部变量、函数调用链都堆在桌上；切换时，把整张桌面的东西打包收进柜子（另一个任务的 TCB 指向的栈区），再把 B 的桌面从柜子里搬出来。这就是为什么**每个任务必须有一块独立的栈**——它们各自的内存互不污染。

栈的大小在创建任务时指定：

```c
#define TASK_STACK   256          // 单位：字（word），即 256*4 = 1024 字节
StackType_t stack[512];
xTaskCreate(task_sample, "sample", TASK_STACK, NULL, 2, NULL);
```

栈给小了，函数嵌套稍深、局部数组稍大，就会**溢出**——覆盖掉相邻内存（TCB、别的变量），表现通常是莫名其妙的 HardFault，且出错位置和真正原因毫无关系，极难定位。

## 3.6 检测栈溢出

FreeRTOS 提供两种栈溢出钩子（`configCHECK_FOR_STACK_OVERFLOW`）：

- 方式一：在栈末尾放一个「哨兵值」，切换时检查它是否被改写；
- 方式二：检查 SP 是否越过了栈底。

溢出时调用 `vApplicationStackOverflowHook(task, name)`，你可以在里面点灯、打印、复位。上板调试第一件事，就是**打开栈溢出检查**，再用 `uxTaskGetStackHighWaterMark()` 读取「栈水位线」——它返回历史上栈还差多少到顶，数值越小说明栈越吃紧，据此把 `TASK_STACK` 调到安全值。

## 3.7 为什么切换有成本，却值得

一次上下文切换在 72MHz 的 M3 上大约几微秒，期间 CPU 不能干正事。所以**别把时间片切得太碎**，也别用超高频率的 tick 强行轮询。但相比它换来的「确定性响应 + 模块化」，这点开销通常可以忽略。理解「切换 = 换栈 + 存寄存器」，你就理解了 RTOS 一半的灵魂。
