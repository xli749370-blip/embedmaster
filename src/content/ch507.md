# 第七章 软件定时器与事件驱动

> 到第六章为止，我们一直在「预先切好任务」这条路线上走：采集一个、上报一个、指示一个，各自占一个栈。但实际项目里有一大类需求长得完全不一样——它不需要一个常驻任务，只需要「每 500 ms 干一件事」。
>
> 为这种事开一个任务，就像为了每天倒一次垃圾专门雇一个人。软件定时器就是那个「共享的钟点工」。

## 7.1 硬件定时器为什么不够用

STM32F103C8T6 有几个定时器？查手册：TIM1（高级）、TIM2/3/4（通用）、TIM5（通用，大容量型号才有）。C8T6 是 48 脚小容量型号，实际可用的是 **TIM1、TIM2、TIM3、TIM4**，外加 SysTick。

而一个真实产品需要多少路周期动作？随手列一下：

| 需求 | 周期 | 需要什么 |
| --- | --- | --- |
| 传感器采样 | 100 ms | 周期 |
| 屏幕刷新 | 33 ms | 周期 |
| 心跳指示灯 | 500 ms | 周期 |
| 通信超时检测 | 3000 ms | 单次（收到数据就重置） |
| 按键长按判定 | 1000 ms | 单次（按下时启动，松开取消） |
| 自动关机 | 30000 ms | 单次（无操作启动） |
| 数据上报 | 60000 ms | 周期 |

七路，硬件只有四个。而且 TIM2/TIM3/TIM4 里通常还要拿去做 PWM 输出（呼吸灯、电机），根本腾不出来。

有人说「用一个硬件定时器 + 一个全局计数器不就行了」——那你就得自己写这个调度器：维护一张表、算最小公约数、每次中断遍历所有项、处理溢出。**这就是 FreeRTOS 软件定时器干的事，而且它已经写好了、测过了。**

## 7.2 一个任务管所有定时器

软件定时器的架构只有三层：

```
SysTick 中断          守护任务（Timer Service Task）        定时器链
   │                          │                                │
   │ xTickCount++             │ 醒来后遍历链                    ├─ T1 100ms 周期
   ├─────────────────────────>│ 剩余 = 到期时刻 - 现在          ├─ T2 150ms 单次
   │  唤醒守护任务             │ 到期的 → 调回调 → 重装/摘除     └─ T3 200ms 周期
                              │                                      ▲
   用户调用 xTimerStart ──> 命令队列 ──> 守护任务收命令 ──────────────┘
```

三个关键点：

1. **不占用任何硬件定时器。** 时间全部由 SysTick 的 tick 计数推导，1 tick 就是最小分辨率。
2. **回调不在中断里跑。** 中断只负责把 tick 加一、把守护任务唤醒；真正的回调在**守护任务（daemon task）**的上下文里执行。
3. **启动/停止是「发命令」不是「改内存」。** `xTimerStart()` 本质是往命令队列里塞一条消息，守护任务收到后才真正修改链表。所以它有返回值 `pdPASS / pdFAIL`（队列满了就失败）。

动画里 T2 是最值得看的那个：150 ms 的单次定时器，触发一次之后进度条变灰、状态变成「已从链表摘除」，之后再也不会触发。而 T1 每次到期都把 `remaining` 重装回 100，永远活着。

**这就是 `pdTRUE` 与 `pdFALSE` 那个参数的唯一区别**——auto-reload 与否。

## 7.3 六个 API 和它们的真实语义

| API | 做什么 | 有没有坑 |
| --- | --- | --- |
| `xTimerCreate` | 创建，**此时还没启动** | 创建不启动，很多人以为创建完就开始跑 |
| `xTimerStart` | 启动，或重启已经在跑的 | 从没启动过的定时器，从「调用时刻 + period」开始算 |
| `xTimerStop` | 停止，从链表摘除 | 剩余时间丢失，再 `Start` 会重新从整周期开始 |
| `xTimerReset` | 把到期时刻重置为「现在 + period」 | 才是「喂狗」和「无操作超时」的正确姿势 |
| `xTimerChangePeriod` | 改周期并重启 | 会**重置**当前进度，不是「改完继续按新周期走」 |
| `xTimerDelete` | 删除，释放内存 | 回调正在执行时删自己会崩，要用 `xTimerStop` |

一个容易误会的点：**`xTimerStart` 对已经在跑的定时器是「重启」语义**。所以「收到数据就推后 3 秒超时」这种需求，用 `xTimerStart` 和 `xTimerReset` 效果一样；但语义上应该用 `xTimerReset`，因为它明确表达「重新计时」。

```c
static TimerHandle_t xLedTimer = NULL;
static TimerHandle_t xTimeoutTimer = NULL;

/* 回调原型：参数是定时器句柄本身，不是 user_data —— 这是 FreeRTOS 的约定 */
static void vLedCallback(TimerHandle_t xTimer)
{
    (void)xTimer;
    HAL_GPIO_TogglePin(LED_GPIO_Port, LED_Pin);
}

static void vTimeoutCallback(TimerHandle_t xTimer)
{
    (void)xTimer;
    /* 3 秒没收到数据：把链路标记为断开，让上报任务去处理 */
    link_set_state(LINK_DOWN);
    /* 注意：这里不能做耗时操作，也不能 vTaskDelay */
}

void app_timer_init(void)
{
    /* 参数依次：名字、周期(tick)、自动重装、定时器 ID、回调 */
    xLedTimer = xTimerCreate("led", pdMS_TO_TICKS(500), pdTRUE,  (void *)0, vLedCallback);
    xTimeoutTimer = xTimerCreate("tout", pdMS_TO_TICKS(3000), pdFALSE, (void *)1, vTimeoutCallback);

    configASSERT(xLedTimer != NULL);
    configASSERT(xTimeoutTimer != NULL);

    xTimerStart(xLedTimer, 0);
    /* 超时定时器先不启动，等真正发请求的时候再 xTimerReset */
}

/* 串口中断里收到一个字节：喂一次超时定时器 */
void HAL_UART_RxCpltCallback(UART_HandleTypeDef *huart)
{
    BaseType_t woken = pdFALSE;
    xTimerResetFromISR(xTimeoutTimer, &woken);   /* 中断里必须用 FromISR 版本 */
    portYIELD_FROM_ISR(woken);
}
```

## 7.4 回调里的三条纪律

软件定时器的回调跑在守护任务里，而**守护任务是全系统共用的一个任务**。这意味着你在回调里干的任何事，都会影响所有定时器。

**纪律一：不许阻塞。**
回调里出现 `vTaskDelay()`、`xQueueReceive(..., portMAX_DELAY)`、等一个永远不来的信号量——所有定时器会一起停摆。因为守护任务被你卡住了，它没法去巡检链表。表现出来是「灯不闪了、上报停了、超时也不触发了」，而你会去怀疑硬件。

**纪律二：不许用非 0 阻塞时间调用定时器 API。**
在回调里调 `xTimerStart(t, 100)` 会死锁：`xTimerStart` 要往命令队列里塞命令，队列满时它要等，而队列的消费者正是**正在执行你这段回调的守护任务自己**。FreeRTOS 文档明确要求，回调里的定时器 API 阻塞时间必须是 0。

**纪律三：不许做重活。**
一次回调应该几微秒到几十微秒。要处理 1 KB 数据、要写 Flash、要算 FFT——把信号量丢给业务任务，让业务任务去干。

```c
/* 正确姿势：回调只负责「通知」 */
static void vSampleCallback(TimerHandle_t xTimer)
{
    (void)xTimer;
    /* 这是任务上下文，用非 ISR 版本才是正确语义 */
    xSemaphoreGive(xSampleSem);
}
```

这段代码里用 `xSemaphoreGive()` 而不是 `xSemaphoreGiveFromISR()`，是有讲究的：**定时器回调是任务上下文，不是中断上下文**。很多模板统一写成 FromISR 版本，看着「安全」，其实语义错了——FromISR 版本要求你传入 `pxHigherPriorityTaskWoken` 并在中断末尾 yield，放在任务里反而多余。

判断一个回调跑在哪，只需要问一句：**它是不是被中断直接调用？** 定时器回调不是，所以它是任务上下文。这也解释了为什么回调里可以调用那些「只允许在任务里调用」的 API。

## 7.5 硬件定时器 / 软件定时器 / 独立任务，三选一

| 维度 | 硬件定时器 | 软件定时器 | 独立任务 |
| --- | --- | --- | --- |
| 精度 | 纳秒~微秒级，独立于 CPU 负载 | 1 tick，受守护任务调度延迟影响 | 1 tick 起，取决于优先级 |
| 数量 | 芯片有几个就几个 | 受 RAM 限制（每个约 40~60 字节） | 每个要几百字节栈 |
| 抖动 | 极小（硬件比较） | 有，守护任务被抢占就延后 | 有，取决于调度 |
| 回调上下文 | 中断 | 守护任务（任务上下文） | 自己的任务 |
| 适合 | PWM、输入捕获、精确延时 | 周期性的轻量动作（灯、扫描、超时） | 需要阻塞等待的循环业务 |

三条判据：

1. **要输出波形或测量脉冲宽度** → 必须硬件定时器，软件定时器做不到。
2. **只是「到点了提醒我一下」** → 软件定时器，一个字节的开销都不用多花。
3. **到点之后要阻塞地做一长串事**（等 I2C 应答、等 ADC 转换） → 用定时器回调发信号，让独立任务去做。**别在回调里阻塞，这是纪律一。**

## 7.6 五个必踩的坑

**坑一：把 `xTimerCreate` 当成「创建即启动」。**
创建完不 `xTimerStart`，回调永远不执行，而且没有任何报错。现象是「代码明明写了，灯就是不闪」。**排查第一步永远是 `xTimerIsTimerActive()`。**

**坑二：守护任务优先级配低了。**
`configTIMER_TASK_PRIORITY` 如果比业务任务低，而这个业务任务又是个死循环占满 CPU，那么所有定时器会集体迟到。表现是「周期 100 ms 的定时器实际 130 ms 才跑」。规范做法是把它配到**所有任务里最高**（或次高），因为它的回调应该最短。

**坑三：以为周期定时器不会漂。**
周期定时器的重装基准是「守护任务处理到它的那一刻」，不是「上一次的理论到期时刻」。守护任务每次延迟 2 ms，周期就会往后漂 2 ms，长期累积误差可能到秒级。**任何需要长期准时的场景（RTC 打点、长时间平均采样率）都不要用软件定时器，用硬件定时器或 tick 计数自己算。**

**坑四：命令队列溢出。**
`configTIMER_QUEUE_LENGTH` 默认 10。如果在短时间内疯狂调用 `xTimerReset`（比如串口每收一个字节喂一次狗，115200 波特率下每秒 11520 次），队列会满，`xTimerResetFromISR` 返回 `pdFAIL`，狗就喂不上了。**正确做法是：在中断里只置个标志，或者把队列长度调大，并且检查返回值。**

**坑五：在回调里删除自己。**
`xTimerDelete(xTimer, 0)` 在它自己的回调里调用，会让守护任务操作一块刚被释放的内存。要停就 `xTimerStop`，删除放到业务任务里做。

## 7.7 本章小结

- 软件定时器不占硬件资源，用 SysTick 的 tick 推时间，靠守护任务巡检链表。
- 回调跑在**守护任务的任务上下文**，不是中断上下文——所以能用任务级 API，但绝不能阻塞。
- 创建不等于启动；`Start` 是重启语义，`Reset` 才是「重新计时」。
- 单次定时器到期自动摘除，周期定时器自动重装；重装基准是处理时刻，会累积漂移。
- 回调三条纪律：不阻塞、不用非 0 阻塞时间调 API、不做重活。
- 五个坑：创建当启动、守护优先级太低、以为不漂、命令队列溢出、回调里删自己。

## 结语：RTOS 的三件套配齐了

到这里，FreeRTOS 的三大件全部讲完了：

| 组件 | 解决什么 | 认知要点 |
| --- | --- | --- |
| 任务 + 调度 | 「同时做多件事」 | 优先级抢占，栈自己给够 |
| 队列 / 信号量 / 通知 / 事件组 | 「多件事之间怎么说话」 | 传数据用队列，传状态用事件组，传信号用通知 |
| 软件定时器 | 「到点做一件事」 | 回调不是中断，守护任务会被你拖累 |

这三件套之外的一切——内存管理、临界区、低功耗——都是围绕它们的工程细节。掌握这三件套，你就能把一个裸机项目重构成可维护的实时系统；而这也是「综合项目实战」里那台温湿度节点真正落地的方式。
