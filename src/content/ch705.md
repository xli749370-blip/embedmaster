# 第五章 HardFault：让崩溃自己开口说话

[[anim:fault-stack]]

板子跑着跑着"死了"，复位了事是最低级的处理方式。HardFault 触发的那一刻，现场信息其实全在栈上：出事时的 PC、LR、xPSR——定位到代码行只差一层"翻译"。这一章建立一套完整的取证流程：Fault 类型怎么分类、栈帧怎么找、PC 值怎么换算回代码行、什么情况会出现"取到的 PC 是对的却看不到代码"。

## 5.1 Fault 家族：先分诊再定位

Cortex-M 的异常模型把错误分成四级，HardFault 是兜底：

| 异常 | 典型诱因 | 能否 precise |
| --- | --- | --- |
| BusFault | 访问非法地址（未映射区、外设时钟未开就读寄存器） | 是（BFAR 有效时） |
| MemManage | MPU 保护区访问、栈越界撞保护区 | 是 |
| UsageFault | 除零、未对齐访问（编译器一般已避免） | 是 |
| HardFault | 上述 Fault 未使能时的兜底、向量表取指失败、开 `fault` 期间的嵌套 fault | — |

开工程建议第一时间打开三个使能位，让错误细分类而不是全挤进 HardFault：

```c
SCB->SHCSR |= SCB_SHCSR_USGFAULTENA_Msk | SCB_SHCSR_BUSFAULTENA_Msk | SCB_SHCSR_MEMFAULTENA_Msk;
```

进了 Fault 处理函数，第一件事读两个状态寄存器：

- **SCB->CFSR**（0xE000ED28）：细分原因。低 16 位 MemManage，中间 16 位 BusFault（`PRECISERR` = 精确总线错，出错地址在 BFAR；`IMPRECISERR` = 非精确，**地址不可信**，多半是写缓冲延迟所致），高 16 位 UsageFault。
- **SCB->HFSR**（0xE000ED2C）：`FORCED` 位为 1 表示"其实是别的 fault 没使能被升级上来的"——**看到 FORCED 就回去开使能位**，别在 HardFault 里白忙。

## 5.2 取证第一步：找到栈帧

Fault 触发瞬间，硬件已把 xPSR/PC/LR/R12/R3~R0 八个寄存器压栈。取证的难点是**搞不清当时用的 MSP 还是 PSP**（裸机几乎都是 MSP；跑 RTOS，Fault 可能发生在任务里，用的就是 PSP）。标准写法是裸汇编桩：

```asm
HardFault_Handler:
    tst   lr, #4           /* EXC_RETURN bit2 = 1 → 用 PSP */
    ite   eq
    mrseq r0, msp
    mrsne r0, psp
    b     HardFault_c      /* r0 = 栈帧指针，交给 C 函数 */
```

C 侧拿到 `frame` 指针后，按顺序读 8 个字：

```c
void HardFault_c(uint32_t *frame) {
    uint32_t pc  = frame[6];   /* 出错指令地址 */
    uint32_t lr  = frame[5];   /* 出错前最后一次调用点 */
    uint32_t psr = frame[7];
    /* psr 低 9 位是 T 位与异常号：T=0 表示试图切 ARM 模式（向量表填错） */
}
```

## 5.3 从 PC 到代码行：三次换算

拿到 PC 值（比如 `0x0800_1F4A`），三步定位：

1. **换算闪存偏移**：减去闪存基址 `0x0800_0000`，得 `0x1F4A`。
2. **对 MAP 文件**：找"区间覆盖 0x1F4A"的符号——MAP 里每个函数列出起始地址与大小，锁定函数。
3. **对反汇编**：`arm-none-eabi-objdump -d xxx.elf` 找 `1f4a:` 那条指令；若是 IDE（Keil/IAR/CubeIDE），直接在 Fault 窗口看调用栈。

$$\text{代码行} = \text{map 查表}\left(\text{PC} - \text{FLASH\_BASE}\right)$$

两种"取到怪 PC"的情形要认识：

- **T 位被清零**（xPSR bit24 = 0）：Cortex-M 只有 Thumb 指令，T=0 意味着跳到了一个"地址没加 1"的函数指针——**向量表或函数指针填错**，而非真的访问了坏地址。
- **PC 落在数据区 / 0xFFFFFFxx**：栈被踩、返回地址被覆盖，此时取证方向改为"谁踩了栈"（回到第四章的水位线与 MPU 方案）。

## 5.4 非精确错误的排查套路

`IMPRECISERR` 最烦人：BFAR 无效，出错地址未知。原因是**写缓冲**——CPU 把写操作扔进缓冲就继续跑，几拍后总线才真正执行并报错，现场早已漂移。

排查三板斧：

1. **临时关写缓冲**：`SCnSCB->ACTLR |= 2;`（禁用写缓冲，性能略降）。若从此变成 `PRECISERR`，说明原地址仍可找，只是被缓冲延迟了。
2. **缩小嫌疑集**：最近一次改动涉及的写操作（外设寄存器写、DMA 缓冲写、栈上大对象）。
3. **二分回滚**：注释掉一半新代码跑，反复二分定位。

实践中 90% 的 BusFault 是这几件事：**外设时钟没开就去读寄存器**、**DMA 的缓冲区放进了 CPU 无法访问的 CCM RAM**、**数组越界写到了未映射区**、**对 `NULL` 的指针写**（0x0000_0000 附近没映射有效 RAM 时触发）。

## 5.5 把 Fault 变成可复现的测试用例

成熟的工程不满足于"现场看一眼"，而是把 Fault 处理固化：

1. **保留现场**：栈帧 8 字 + CFSR/HFSR/BFAR/MMFAR + 版本号 + 复位原因，打包成一条"黑匣子记录"写进 **不会掉的备份寄存器（RTC 备份域）** 或 Flash 末页。
2. **软复位**：`NVIC_SystemReset()` 让设备自动恢复。
3. **开机上报表**：复位后读黑匣子，通过串口/日志上云。
4. **线下回放**：拿黑匣子里的 PC/LR 对 MAP 复盘，转化成一个可复现的测试用例修掉。

这套流程的价值在量产：设备在现场死机，你不用到场也能拿到与实验室等价的证据链。

## 5.6 五个经典坑

1. **Fault 处理函数里再 fault**：栈已满还往里压、打印函数本身出错 → 系统彻底锁死。处理函数保持极简，只用静态缓冲。
2. **RTOS 下不用 MSP/PSP 双查**：只读 MSP 会取到内核栈，误判现场。
3. **看到 FORCED 还硬啃 HardFault**：先开三个 fault 使能位复现，细分原因浮出来再查。
4. **把 `IMPRECISERR` 的 BFAR 当真**：该寄存器此时无效，照它排查会南辕北辙。
5. **Flash 等待周期不足导致的"随机 HardFault"**：主频提到 72 MHz 而 WS 没设 2，取指偶发出错，现象是"跑几小时死一次"，与逻辑 bug 极难区分。

## 5.7 本章小结

- 先分诊：**CFSR 细分原因，HFSR.FORCED = 1 → 回去开 fault 使能位**。
- 栈帧必经**汇编桩判 MSP/PSP**，frame[6] = PC、frame[5] = LR。
- 定位三换算：**减闪存基址 → MAP 找函数 → objdump 找指令**。
- **T 位为 0 = 函数指针/向量表没加 1**；PC 落数据区 = 栈被踩。
- 非精确错误先**关写缓冲**再排查；量产方案是**黑匣子 + 软复位 + 开机上报**。
