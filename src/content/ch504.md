## 4.1 多任务的第一道坎：竞态

两个任务同时跑，最容易出的问题是**竞态（Race Condition）**：它们共享同一份资源——一个全局缓冲区、一块硬件寄存器、一个文件句柄——且至少一方会写它。

看一个经典翻车现场：任务 A 和任务 B 都要往同一个串口打印，A 刚打印了一半，tick 到来，调度器切到 B，B 也开打印。结果屏幕上 A 和 B 的字符**交错成一团乱码**。根源是「打印这一段」不是原子操作，中途被打断了。

解决共享资源冲突，FreeRTOS 给了三件套：**临界区、信号量、互斥量**；而任务之间要「传数据」，则用**消息队列**。本章逐一讲清它们各自的适用场景。

## 4.2 二值信号量：同步与门禁

信号量本质是一个**计数值**。二值信号量只有 0 和 1 两种状态，常用于两类事：

**① 任务同步（ISR → 任务）。** 中断里不宜做重活，标准做法是：ISR 收到数据后，调用 `xSemaphoreGiveFromISR()` 给一个信号量「置 1」，唤醒平时阻塞在 `xSemaphoreTake()` 上的任务去处理。这样**中断只负责「敲一下门」，真正干活在任务里**，绝不阻塞中断。

```c
void USART1_IRQHandler(void) {            // 中断里
    recv = USART1->DR;
    xSemaphoreGiveFromISR(xNewData, NULL);// 仅置位，极快
}
void task_proc(void *p) {                  // 任务里
    for (;;) {
        xSemaphoreTake(xNewData, portMAX_DELAY); // 阻塞等，不空转
        process(recv);
    }
}
```

**② 资源门禁。** 某资源同一时刻只允许一个使用者，就让它持有信号量，用完 `Give` 释放。但门禁场景更推荐用互斥量（见 4.4），因为信号量没有「优先级继承」，会踩到下面的反转坑。

## 4.3 计数信号量：资源池

如果资源不是「一个」，而是一池子（比如 5 个缓存块、3 个连接槽），用**计数信号量**，初值设成资源数量。每次取一个 `Take` 计数减一，释放一个 `Give` 计数加一；计数为 0 时再取就阻塞。它天然适合「有限资源池」的模型。

## 4.4 互斥量：为「保护共享」而生

互斥量（Mutex）也是二值，但多了一个关键能力——**优先级继承（Priority Inheritance）**。要理解它，先看经典事故：

> **优先级反转（Priority Inversion）。** 任务 H（高）、M（中）、L（低）。L 先跑，拿了锁去访问共享资源。此时 H 就绪，抢占 L 开始跑，H 也要那把锁，于是 H 阻塞等 L 释放。按理说 M 优先级低于 H，不该插队——但此刻 L 还在持有锁慢慢跑，M 却因为「不抢那把锁」而能被调度，于是 **M 在 H 之前跑了**。高优先级 H 被低优先级 M 间接堵住，顺序完全乱套。

互斥量的解法：当 H 等 L 的锁时，内核**临时把 L 的优先级提升到和 H 一样**，让 L 尽快跑完、释放锁，H 随即拿到锁。等锁释放后再把 L 降回原优先级。这样 M 没机会插队，反转被「拉平」。这就是优先级继承。

> 经验：纯粹「保护一段共享代码/数据」，**无脑用互斥量**；「发事件通知」才用信号量。互斥量**不能在中断里用**（中断不能阻塞），中断里只能用信号量。

## 4.5 消息队列：任务间传数据

信号量只能「敲门」，没法把数据带过来。要传数据，用**消息队列（Queue）**：一段内核管理的环形缓冲区，支持：

- **FIFO / 可选 LIFO**；
- **阻塞发送与接收**：队列满时发送者阻塞，空时接收者阻塞，不用轮询；
- **传值或传引用**：小数据直接拷贝进队列（安全，无生命周期问题）；大数据传指针，但要保证发送期间那块内存不被释放；
- **队首/队尾插入**、甚至**向所有等待者广播**。

```c
QueueHandle_t q = xQueueCreate(10, sizeof(int)); // 10 个 int 的队列
xQueueSend(q, &value, portMAX_DELAY);            // 任务里发送
xQueueReceive(q, &value, portMAX_DELAY);          // 阻塞等数据
```

队列是 RTOS 里**用得最多**的通信原语。一个经典架构：ISR 收完一帧塞进队列，N 个Worker 任务排队取出来处理，天然解耦「采集」与「计算」。

[[anim:queue-block]]

注意时间轴上灰色（Blocked）那几拍的真正含义：Worker **并没有在 while 里空转检查队列**，它已经从就绪列表里被摘掉了，调度器根本不会选它——这段时间 CPU 可以去跑低优先级任务，或者干脆进 WFI 睡觉。等到 ISR 里 `xQueueSendFromISR` 把数据塞进队列，内核才把它挪回就绪列表（橙色 Ready），等 ISR 退出、PendSV 挂起后才完成真正的切换（绿色 Running）。

这解释了一个常见疑惑：「阻塞会不会浪费 CPU？」——恰恰相反，**轮询才浪费**。用 `xQueueReceive` 阻塞等数据，等待期间 CPU 占用是零；用全局 flag 加 `while(!flag)` 轮询，那是把一整个核心的空转时间全烧掉，还挡住了所有低优先级任务。

顺带说清三个容易混的参数：阻塞时间 `portMAX_DELAY` 表示永久等待（仅当 `INCLUDE_vTaskSuspend` 为 1 时才是真永久）；传 `0` 表示不等，队列空就立刻返回 `pdFALSE`；传具体 tick 数则是「最多等这么久」。**ISR 里一律用带 `FromISR` 后缀的版本，且超时参数不能是 `portMAX_DELAY`。**

## 4.6 任务通知与事件组：两个更轻的替代品

信号量和队列都有同一个「重」的地方：它们都是**独立的内核对象**，有自己的控制块，创建时要分配内存，发一次要做链表操作。对于「ISR 告诉任务有数据来了」这种最高频的场景，FreeRTOS 提供了两条更轻的路。

### 任务通知：往目标任务的 TCB 里直接写字

每个任务在 TCB 里自带一个 32 位值（`ulNotifiedValue`）和一个状态位。ISR 或别的任务可以直接往这个值里写，内核顺手把目标任务挪到就绪列表——**没有中间对象，没有内存分配，没有数据拷贝**。

```c
/* 发送方（任务或 ISR） */
vTaskNotifyGiveFromISR(g_hWorker, &xHigherPriorityTaskWoken);
/* 或从任务里 */
xTaskNotifyGive(g_hWorker);

/* 接收方：等一个通知，取走并把计数清零 */
ulTaskNotifyTake(pdTRUE, portMAX_DELAY);
```

它比二值信号量快大约 45%，也更省 RAM（每次约 5 字节，而不是一个完整的信号量对象）。代价有三个，都很硬：

1. **只能有一个接收方**。通知是写进「某个任务的 TCB」的，天然点对点，做不到「一个事件唤醒三个任务」。
2. **只有一个 32 位值**。想同时表达「数据到了」和「是第几路数据」，得自己把位拆开用。
3. **发送方必须知道接收方的句柄**。这让模块之间的耦合变紧——B 模块要给 A 模块发通知，就必须持有 A 的任务句柄。

### 事件组：多源多位的「状态板」

事件组是一块（默认）**24 位的寄存器**，每个 bit 代表一件事。多个来源各自置位，接收方可以选「任意一位置位就醒」或「我指定的这几位全置位才醒」：

```c
#define BIT_SENSOR  (1 << 0)
#define BIT_KEY     (1 << 1)

/* 各个 ISR 各自置自己那一位 */
xEventGroupSetBitsFromISR(g_eg, BIT_SENSOR, &xHigherPriorityTaskWoken);

/* 接收方：等 bit0 和 bit1 都置位，等到后自动清掉这两位 */
EventBits_t bits = xEventGroupWaitBits(
    g_eg,
    BIT_SENSOR | BIT_KEY,   /* 关心哪些位 */
    pdTRUE,                 /* 退出时清除这几位 */
    pdTRUE,                 /* pdTRUE = 全部置位才返回；pdFALSE = 任一即可 */
    portMAX_DELAY);
```

事件组的关键差别在于：**位代表的是「状态」，不是「消息」**。同一个事件来了两次，位还是那一位（不会变成 2）；而任务通知的计数会累加到 2。而且事件组可以被**多个任务同时等待**，一个源置位能唤醒所有关心这一位的任务。

[[anim:notify-event]]

动画里最值得盯的是第 3 拍：通知值被 `ulTaskNotifyTake` 取走后归零，而事件组的 bit0 还亮着。这一格就是选型的全部判据：

- 要传 **「事情发生了几次 / 带一个计数值」** → 用任务通知，取一次少一次。
- 要表达 **「现在处于什么状态」**，或者需要**多个任务、多个条件组合** → 用事件组，位必须显式清除（`xEventGroupClearBits`），忘了清就会「第二次不触发」。

事件组也有代价：它的置位/清除在内部是关中断的临界区，**不适合高频调用**。几毫秒一次没问题，几十微秒一次就会明显吃掉实时性。

## 4.7 怎么选：一张决策表

| 你想做的事 | 用哪个 |
| --- | --- |
| 中断通知任务「有数据/事件来了」 | 二值信号量（FromISR 版本） |
| 中断通知**某一个特定任务**，且要最快最省 | 任务通知（`vTaskNotifyGiveFromISR`） |
| 一个事件要唤醒**多个**任务，或多源汇聚后组合判断 | 事件组（`xEventGroupSetBitsFromISR`） |
| 保护一段共享代码或变量不被同时改 | 互斥量 Mutex |
| 管理有限数量的资源（连接/缓存块） | 计数信号量 |
| 任务之间传递一段实际数据 | 消息队列 Queue |
| 极短、不进任务的临界片段 | 临界区（关中断/调度锁） |

记住一条铁律：**不要把共享变量裸奔**。要么用互斥量护住，要么通过队列把数据「递」过去，而不是让两个任务直接戳同一块内存。

## 4.8 一个常见的误用

新手爱写「全局变量 + volatile + 轮询 flag」来通信，觉得比队列简单。但 volatile 只保证可见性，不保证原子性，也不保证顺序——多个任务同时写同一变量照样出错。RTOS 提供了这么多原语，就是让你**别再手写脆弱的共享内存协议**。能用队列表达的数据流，就别用全局变量。
